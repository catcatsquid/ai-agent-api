## 一、上下文切换（进程切换）

### 什么是上下文切换

上下文切换是操作系统将 CPU 从一个进程切换到另一个进程的过程。"上下文"指进程运行时 CPU 寄存器的状态（程序计数器 PC、通用寄存器、栈指针 SP 等），这些信息保存在进程控制块（PCB）中。

### 上下文切换的步骤

1. **保存当前进程上下文**：将当前 CPU 寄存器状态（PC、SP、通用寄存器等）保存到当前进程的 PCB 中
2. **更新 PCB 状态**：将当前进程的状态从"运行态"改为"就绪态"或"阻塞态"
3. **选择新进程**：调度器从就绪队列中选择下一个要运行的进程
4. **恢复新进程上下文**：从新进程的 PCB 中读取寄存器状态，加载到 CPU 中
5. **跳转到新进程**：CPU 从新进程的 PC 处继续执行

### 上下文切换的开销

- **直接开销**：保存和恢复寄存器、切换页表（TLB 刷新）、调度算法执行时间
- **间接开销**：CPU 缓存失效（Cache miss），TLB 失效导致地址转换变慢
- 上下文切换是纯系统开销，切换期间不做有用工作，应尽量减少

### 上下文切换与模式切换的区别

- **模式切换**（用户态 ↔ 内核态）：同一进程内，通过系统调用或中断进入内核态，开销小
- **上下文切换**：不同进程间切换，需要保存/恢复完整 PCB，开销大
- 模式切换是上下文切换的前提（系统调用 → 内核态 → 调度 → 上下文切换）

## 二、银行家算法

### 背景

银行家算法是 Dijkstra 提出的死锁避免算法。名字来源于银行家贷款的比喻：银行家有一笔资金（系统资源），多个客户（进程）申请贷款（请求资源），银行家要确保贷款后自己不会陷入资金短缺（不安全状态），否则拒绝贷款。

### 核心概念

- **可用资源（Available）**：系统当前各类资源的可用数量
- **最大需求（Max）**：每个进程最多需要的各类资源数量
- **已分配（Allocation）**：当前已分配给每个进程的各类资源数量
- **需求（Need = Max - Allocation）**：每个进程还需要的各类资源数量

### 安全状态判断流程

1. 计算每个进程的 Need = Max - Allocation
2. 设 Work = Available（当前可用资源副本），Finish[i] = false（所有进程未完成）
3. **循环查找**：找一个进程 i，满足 Finish[i] = false 且 Need[i] ≤ Work
4. **模拟释放**：找到这样的进程 i 后，Work += Allocation[i]，Finish[i] = true（进程执行完毕释放资源）
5. 重复步骤 3-4，直到找不到满足条件的进程
6. **判断**：如果所有 Finish[i] = true，则系统处于安全状态，存在安全序列；否则不安全

### 安全序列

安全序列是进程执行完成的一个顺序，保证每个进程都能获得所需资源顺利执行完毕。

例如：进程集合 {P0, P1, P2, P3, P4}，安全序列 <P1, P3, P4, P0, P2> 表示按此顺序分配资源，每个进程都能完成。

### 资源请求处理流程

当进程 Pi 请求资源 Request[i] 时：
1. 检查 Request[i] ≤ Need[i]（请求不超过最大需求）
2. 检查 Request[i] ≤ Available（请求不超过可用资源）
3. **试探分配**：Available -= Request[i]，Allocation[i] += Request[i]，Need[i] -= Request[i]
4. 执行安全性检查（上面的流程），如果安全则真正分配，否则回滚试探分配，让进程等待

### 与死锁预防的区别

- **死锁预防**：破坏四个必要条件之一，限制严格，资源利用率低
- **银行家算法**：允许四个必要条件存在，但在分配前检查安全性，避免进入不安全状态
- 银行家算法需要预先知道每个进程的最大资源需求，现实中难以满足

## 三、页面置换算法

### 背景

当物理内存不足时，需要将某些页面换出到硬盘（swap），选择哪个页面换出就是页面置换算法的任务。目标是减少缺页中断次数。

### 1. OPT 最佳置换算法（Optimal）

- **策略**：选择未来最长时间不会被访问的页面换出
- **优点**：缺页率最低（理论最优）
- **缺点**：无法实现（需要预知未来访问序列）
- 用途：作为其他算法的理论下界评估标准

### 2. FIFO 先进先出置换算法

- **策略**：选择在内存中停留时间最长的页面（最先进入的）换出
- **优点**：实现简单（用 FIFO 队列）
- **缺点**：可能换出频繁使用的页面，存在 Belady 异常（增加物理页数反而缺页更多）
- Belady 异常：FIFO 在增加页帧数时，缺页率可能反而升高

### 3. LRU 最近最少使用（Least Recently Used）

- **策略**：选择最长时间未被访问的页面换出
- **实现方式**：
  - 计数器：每个页面维护一个上次访问时间戳，换出时间戳最小的
  - 栈：页面被访问时移到栈顶，换出栈底页面
- **优点**：性能接近 OPT（基于局部性原理）
- **缺点**：实现复杂，需要硬件支持（计数器或链表更新）

### 4. Clock 时钟算法（又称 Second Chance）

- **策略**：FIFO 的改进版，给每个页面一个访问位（reference bit）
  - 页面被访问时，访问位设为 1
  - 指针按 FIFO 顺序扫描：遇到访问位=1 的页面，置为 0 继续扫描；遇到访问位=0 的页面，换出
  - 第二次机会：如果页面最近被访问过（访问位=1），暂时不换出，给第二次机会
- **优点**：实现简单，性能接近 LRU
- **缺点**：需要硬件支持访问位

### 5. 改进 Clock 算法

同时考虑访问位（R）和修改位（M）：
- (R=0, M=0)：最佳淘汰页（最近未用且未修改）
- (R=0, M=1)：未访问但修改过（写回磁盘开销）
- (R=1, M=0)：最近访问过，未修改
- (R=1, M=1)：最近访问过且修改过（最不应淘汰）
按优先级从低到高扫描淘汰

### 算法对比

| 算法 | 依据 | 优点 | 缺点 | 是否有Belady异常 |
|------|------|------|------|-------------------|
| OPT | 未来访问 | 最优 | 无法实现 | 否 |
| FIFO | 进入顺序 | 简单 | 性能差 | 是 |
| LRU | 过去访问 | 接近OPT | 实现复杂 | 否 |
| Clock | 访问位 | 简单+接近LRU | 需硬件支持 | 否 |

## 四、磁盘调度算法

### 背景

磁盘访问时间 = 寻道时间 + 旋转延迟 + 数据传输时间。寻道时间（移动磁头到目标磁道）是主要开销。磁盘调度算法通过优化磁头移动顺序减少寻道时间。

### 1. FCFS 先来先服务

- 按请求到达顺序依次服务
- 优点：公平，实现简单
- 缺点：磁头移动距离大，性能差

### 2. SSTF 最短寻道时间优先（Shortest Seek Time First）

- 每次选择离当前磁头位置最近的请求
- 优点：平均寻道时间短
- 缺点：可能导致远处请求饥饿（Starvation）

### 3. SCAN 电梯算法

- 磁头沿一个方向移动到底（最远请求），然后反向移动到底
- 类似电梯：一直向一个方向走，服务沿途请求，到顶后反向
- 优点：无饥饿，性能好
- 缺点：两端请求等待时间长

### 4. C-SCAN 循环扫描

- 磁头只沿一个方向服务（如从内到外），到最远后快速返回内侧重新开始
- 返回过程中不服务任何请求
- 优点：各磁道等待时间更均匀
- 缺点：返回移动有时间浪费

### 5. LOOK / C-LOOK

- LOOK：SCAN 的改进，磁头只需移动到最远请求位置即反向，不必走到最底
- C-LOOK：C-SCAN 的改进，磁头移动到最远请求后立即反向
- 实际系统中常用 LOOK 和 C-LOOK

### 算法对比

| 算法 | 策略 | 是否饥饿 | 优点 |
|------|------|---------|------|
| FCFS | 到达顺序 | 否 | 公平简单 |
| SSTF | 最近距离 | 是 | 短延迟 |
| SCAN | 电梯式 | 否 | 均衡 |
| C-SCAN | 单向扫描 | 否 | 均匀等待 |
| LOOK | SCAN改进 | 否 | 减少空移 |

## 五、文件系统

### 文件存储结构

#### 1. 连续分配（Contiguous Allocation）

- 每个文件占用磁盘上连续的物理块
- 目录项记录：起始块号 + 长度
- 优点：顺序访问快（磁头连续移动），随机访问也快（计算偏移即可定位）
- 缺点：外部碎片（文件删除后产生不连续空闲块），文件大小难以动态增长
- 适合：CD-ROM 等只读文件系统

#### 2. 链接分配（Linked Allocation）

- 文件的物理块通过指针链接，每个块末尾存放下一个块的指针
- 目录项记录：起始块号 + 结束块号
- 优点：无外部碎片，文件可动态增长
- 缺点：随机访问慢（需从头遍历链），指针占空间，链断裂风险
- FAT（文件分配表）是链接分配的改进：将所有指针集中存放在FAT表中

#### 3. 索引分配（Indexed Allocation）

- 每个文件有一个索引块，索引块中存放该文件所有数据块的指针
- 目录项记录：索引块地址
- 优点：支持随机访问，无外部碎片
- 缺点：索引块本身占空间，文件很大时索引块不够（需多级索引）
- 多级索引：大文件使用一级索引指向多个二级索引块，类似多级页表

### inode（索引节点）

inode 是 Unix/Linux 文件系统的核心数据结构：

- 每个 inode 存储：文件类型、权限、所有者、时间戳、文件大小、**数据块地址列表**
- inode 不存储文件名（文件名在目录中）
- inode 包含 12 个直接块指针 + 1 个一级间接指针 + 1 个二级间接指针 + 1 个三级间接指针
- 目录结构：目录本身也是一个文件，内容是「文件名 → inode号」的映射表

### 目录结构

- **单级目录**：所有文件在同一目录下，不能重名
- **两级目录**：每个用户一个目录，解决不同用户重名问题
- **树形目录**：多级层次结构，现代操作系统标准
- **无环图目录**：允许文件/目录共享（通过符号链接或硬链接）

### 硬链接 vs 软链接

| | 硬链接 | 软链接（符号链接） |
|---|--------|-------------------|
| 本质 | 多个文件名指向同一 inode | 新文件，内容是目标路径字符串 |
| inode | 相同 | 不同（软链接有自己的 inode） |
| 原文件删除 | 仍可访问（inode 引用计数 >0） | 失效（找不到目标） |
| 跨文件系统 | 不能 | 能 |
| 创建 | ln file hardlink | ln -s file softlink |

## 六、多级反馈队列调度（MLFQ）

### 基本思想

多级反馈队列（Multi-Level Feedback Queue）通过多个不同优先级的队列实现动态调度。新进程进入最高优先级队列，使用完时间片后降级到下一级队列。这样 I/O 密集型进程会自然停留在高优先级（因为它们用不完时间片就阻塞），CPU 密集型进程会逐渐降级。

### 队列结构

- 设置 N 个队列 Q0, Q1, ..., Q_{N-1}，优先级从高到低
- 每个队列有时间片：优先级越高，时间片越短
  - Q0: 时间片 = 2ms
  - Q1: 时间片 = 4ms
  - Q2: 时间片 = 8ms
  - ...
- 新进程进入 Q0（最高优先级）

### 调度规则

1. **优先级调度**：优先级高的队列先执行，同队列内用 RR（时间片轮转）
2. **降级规则**：进程用完当前队列的时间片后，降级到下一级队列
3. **时间片递增**：越低优先级的队列，时间片越大

### 优先级调整

- **用完时间片 → 降级**：进程在当前队列用完整个时间片，降一级
- **未用完时间片（主动放弃 CPU）→ 保持**：进程在时间片内因 I/O 阻塞，回到同一优先级队列尾部
- 这样 I/O 密集型进程（交互式）会保持高优先级，获得快速响应

### 可能的问题与解决

- **问题1：饥饿** — 低优先级队列的进程可能长期得不到执行
  - 解决：**优先级提升（Priority Boost）**，每隔一段时间将所有进程提升到最高优先级
- **问题2：欺骗调度器** — 进程在时间片快用完前故意做 I/O 放弃 CPU，保持高优先级
  - 解决：**累计计时**，记录进程在当前优先级使用的总 CPU 时间，超过阈值才降级，不看单次

### MLFQ 的优点

- 自动适应进程行为：I/O 密集型自动获得高优先级，CPU 密集型降级到低优先级
- 兼顾响应时间和吞吐量
- 无需事先知道进程类型

## 七、CDN 内容分发网络

### 什么是 CDN

CDN（Content Delivery Network）是通过在各地部署边缘服务器节点，将源站内容缓存到离用户最近的节点，用户访问时从最近的节点获取内容，减少延迟和源站压力。

### CDN 工作流程

1. 用户请求域名如 www.example.com
2. DNS 解析时，CDN 的 DNS 服务器返回离用户最近的边缘节点 IP
3. 用户直接访问该边缘节点
4. 边缘节点有缓存则直接返回内容（缓存命中）
5. 边缘节点无缓存则回源站拉取内容，缓存后返回给用户

### CDN 的核心技术

- **DNS 重定向**：通过 DNS 智能调度将用户分配到最近的节点
- **内容缓存**：边缘节点缓存热门内容，减少回源请求
- **内容分发**：源站内容主动推送到各边缘节点
- **负载均衡**：节点间流量调度，避免单点过载

### CDN 缓存命中方式

- **主动推送**：源站主动将内容分发到各节点（适合静态内容预热）
- **被动拉取**：用户首次请求时，节点从源站拉取并缓存（适合长尾内容）
