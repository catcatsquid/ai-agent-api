# 方法论：怎么优化一个 Agent —— 可复用的过程

> 本文不是"某次修复的记录"，而是**从本项目的多次优化里抽出来的做法**。
> 素材来源：5 个用户实测 bug 的根因链、一次「框架版 Agent 悄悄变坏」的排查、
> 一次「两条路径同题对比并追平」的完整过程。
>
> 一句话结论：**优化 Agent 的难点不在"改哪里"，而在"怎么知道真的变好了"。**

---

## 一、整套流程（六步）

```
① 先定义「什么叫更好」   → 判据必须是用户能感知的，分「好/坏」两类
② 建可重复的测量         → 固定脚本 + 多轮 + 探针先自检
③ 拿基线                 → 没有基线就没有"变好了"，只有"我感觉"
④ 定位根因（分层）       → 状态 / 契约 / 路由 / 工具面，四层依次查
⑤ 按「从便宜到贵」修     → 四级阶梯，能便宜解决就别动结构
⑥ 验证 + 固化            → 把发现写成测试；把代价显式化
```

下面每步给出**本项目真实用过的做法和踩过的坑**。

---

## 二、① 定义「什么叫更好」：判据要放在用户能感知的结果上

**反面做法**（我一开始就是这么干的）：用"有没有调用某个工具""走了哪个节点"当判据。

问题：实现细节会变，而且**会被假象骗**。真实例子：
我一开始用「回复里有没有出现文件名」判断「有没有读对那一章」，
结果模型确实读错了章（读了网络层），但**工具提示里带了文件名**，
于是判据显示"命中" —— 判据在替模型说谎。

**改对的做法**：判据用用户能感知的东西。同一个问题的正确判据是
「回复里有没有**该章特有的内容关键词**」（如传输层 → TCP/UDP/端到端）。

**判据还要分两类，坏的权重更高**：

| 类型 | 例子 | 为什么分开 |
|---|---|---|
| 好信号（希望发生） | 讲了课件内容、说了「本节结束」、给了小测 | 缺了只是"不够好" |
| **坏信号（不希望发生）** | 先甩目录、跑去题库批改、自己编题、串到旧课程 | **发生了就是体验事故** |

实测：只看"好信号总数"会得出"两边差不多"的结论；
把坏信号单独统计之后，差距是 **好16/坏3 vs 好18/坏2** ——
**坏信号才是学生真正在意的**。

## 三、② 建可重复的测量：固定脚本 + 多轮 + **探针先自检**

### 3.1 用「扮演用户」的固定脚本，而不是随手问

本项目用的脚本（5 个场景，覆盖一条完整使用链）：

```
我要复习操作系统
→ 我答一下：1.B 2.D 3.对 4.银行家算法
→ 第二题我还是没懂，能换个讲法吗
→ 现在换计算机网络，我要复习传输层
→ 那刷几道传输层的题吧
```

要点：
- **场景要连成一条链**（跨轮状态、上下文、话题切换都在里面）
- **同一段脚本对两个实现各跑一遍**，才是公平对比
- **跑多轮取一致性**，单轮结论不可信（本项目跑 2~3 轮）

### 3.2 ⚠️ 探针先自检 —— 我在这一步错了两次，两次都得出错误结论

| 错误 | 现象 | 后果 |
|---|---|---|
| **发错字段名** | 接口要 `session_id`，我发了 `thread_id`（被 Pydantic 静默忽略） | **每轮都是新会话、状态全丢** → 我把"没有记忆"当成产品缺陷，还去改了代码 |
| **抓错事件名** | 它发 `{"type":"tool"}`，我只抓 `{"type":"node"}` | 误判"工具根本没被调用" |

> **教训：测一个 Agent 之前，先验证你的测量工具。**

**自检清单（跑之前花两分钟，能省一整轮）**：

1. **状态真的跨轮了吗？** 打印一次会话状态确认（别假设）。
2. **工具调用真的抓到了吗？** 先故意问一个必然触发工具的问题，看探针有没有输出。
3. **字段名/事件名是从代码里读的，还是猜的？** 猜的一律去读代码或抓一份原始事件。
4. **判据会不会被"实现痕迹"满足？** （如"回复里有文件名"会被工具提示满足）
5. **失败时能不能看到原始回复全文？** 只留摘要会让诊断无从下手。

## 四、③ 拿基线：没有基线，只有"我感觉"

本项目第一次对比的基线（3 轮 × 5 场景）：

```
BOT 好17 / 坏16   |   助教 好27 / 坏5
```

有了这行数字，后面每一次修复才有"有没有用"的判断依据。
**同时它立刻暴露了"我以为没问题"的地方**：我原以为 BOT 是主力、助教是补充，
基线显示**恰好相反**（在那个流程上）。

**顺便**：基线也要分层看。只报总数会掩盖"某个场景特别烂"
（本项目「按知识点刷题」是 **0/5**，全错，而总数看不出来）。

---

## 五、④ 定位根因：分层查，四层依次过

按"离模型多远"排序，**从最里层往外查**，因为越里层越隐蔽：

| 层 | 问什么 | 本项目的真实例子 |
|---|---|---|
| **① 状态层** | 模型需要的信息，**在它这一刻看得到吗**？ | 学习书签只注入了 planner，**写回答的 synthesizer 看不到** → 讲了课但不说「本节结束」 |
| **② 契约层** | 工具返回值里的契约，**能到达模型吗**？给对了吗？ | `_guide` 在助教侧能到达，在图上那条路被节点分工切断了 |
| **③ 路由层** | 该调的工具，**有没有被规则抢走**？ | 「刷几道传输层的题」被规则 1（刷题→list_papers）先命中 → 永远给试卷菜单 |
| **④ 工具面层** | 这个工具**是否根本不该在这一刻出现**？ | 讲课中它总能想到 `grade_answers` → 最后是"干脆不提供"才治住 |

**分层查的价值**：如果不分层，我第一反应会是"planner 提示词写得不好"，
然后一直改提示词 —— 而真正的根因在最里层（**信息没送到**），
提示词再改也不生效。

> ⭐ 一个反直觉但重要的现象：**最有洞察力的那处修复（状态层）没有直接拉升分数。**
> 它只是让契约"能到达"；真正让指标动的是路由层和工具面层的修复。
> **「找到根因」和「指标改善」不是同一件事，别用指标反过来否定根因判断。**

## 六、⑤ 按「从便宜到贵」修：四级阶梯

**这是本文最实用的一张表。** 同一个问题，先试便宜的；不行再往下走。

| 级 | 手段 | 成本 | 可靠性 | 本项目实例 |
|---|---|---|---|---|
| **1** | **改提示词** | 最低 | **最低**（实测经常不跟） | 「不要用 grade_answers」→ **不跟** |
| **2** | **工具返回值里的契约** | 低 | 中（能结构化到达模型） | `reply_text` 成品文本、`_guide` 呈现契约、`[study-state]` 机器可读行 |
| **3** | **代码守卫**（确定性，绕过模型判断） | 中 | 高 | 「没看到题目」→ **强制重发那一组**（覆盖原计划） |
| **4** | **改变工具面 / 结构**（不给它做错的机会） | 高 | **最高** | 讲课中**不提供**题库工具；`section` 优先按章号解释 |

**真实的三级升级过程**（治「讲课中学生交自拟小测答案，它却跑去题库批改」）：

```
级 1：system prompt 里写「不要用 grade_answers，那是题库真题的通道」  → 不跟，照样问学生"你在做哪份卷子"
级 2：工具入口加硬守卫，返回「这是小测，由你自己批」                    → 不跟，还是问卷名
级 4：讲课中（且无当前试卷）**干脆不给它这个工具**                      → 治住
```

> **规律：能用结构解决的，别用提示词解决。**
> 每往下一级，代价更高但更可靠 —— 而且**级 1 失败不代表级 2/3/4 会失败**。

### 6.1 「结构性纠偏」是本项目反复验证最有效的一招

| 问题 | 提示词解法（失败） | 结构解法（成功） |
|---|---|---|
| 讲课程内容却去读补充笔记 | 「请优先用课件」 | 读到课本/笔记时**工具自动换成课件**并说明 |
| 模型编文件名（`source="操作系统课件"`） | 「不要编文件名」 | **不让它叫资源名**，改成课程 + 节号，材料由工具认 |
| 把目录当回复发给学生 | 「不要直接发目录」 | **不给它 `reply_text`**（目录是内部资料） |
| 学生说「没看到题目」它只道歉 | 「要真的重发」 | **代码覆盖计划**，强制重发那一组 |

**判断标准**：如果这个约束能用"改数据结构 / 改默认值 / 改可选集合"表达，
就不要写成一句话。

## 七、⑥ 验证 + 固化：把发现写成测试，把代价显式化

### 7.1 把发现固化成测试（而不是留在脑子里）

本项目每次排查完都会落一条测试，且**测试名就是结论**，例如：

- `test_read_position_alone_reaches_the_planner` —— 因为"书签没有 course，
  planner 整块提示被静默跳过"这个 bug 太隐蔽，必须有回归
- `test_quiz_answers_are_guarded_during_study` —— 三级升级的最终结论
- `test_section_means_chapter_number_for_chapter_named_courses` —— 章号错位的教训
- `test_only_intentional_differences_remain` —— 两条实现的差异**必须显式登记**

**写测试的两个偏好**（本项目的经验）：
1. **别把数据快照写死**（`== 191` 这种一改数据就红）—— 断言**语义不变量**
2. **测真实的产物**（真 HTML、真注册表），不要测替身

### 7.2 把「代价」显式化

当一个架构决定带来长期成本时，**把成本写成代码或测试**，别靠记性。
本项目例子：两条实现 = 每加一个能力要写两遍 →
加 `tests/test_surface_parity.py`，让"两边能力不对齐"直接测试失败
（差异必须在 `INTENTIONAL_BOT_ONLY` 里**显式登记**）。

> **代价可见，才是可控的。**

## 八、反面模式（都是我真实踩过的）

| 反面模式 | 为什么坏 | 正确做法 |
|---|---|---|
| **解析自然语言的返回值来存状态** | 措辞一变就断（我按"下次用 offset=15 继续"这句解析，结果 `study` 里没有 course，整块提示被静默跳过） | 让工具输出**机器可读的一行**（如 `[study-state] course=… source=…`） |
| **给模型"成品文本"却忘了它是给学生的** | 模型被教过"成品文本就直接转发" → 把内部目录发给了学生 | 内部资料用**另一个字段名**（`material_map`），并写明"不要作为回复" |
| **契约写给了错误的节点** | 写给 planner 的契约，synthesizer 看不到；而"出小测/本节结束"是写作答的 | 问一句"**这一刻是谁在写回复？它看得到吗？**" |
| **让模型叫出资源名** | 它会编（`source="操作系统课件"`），然后拿不到资料就凭记忆讲 | 让它给**有限集合里的编号/名称**，由工具解析 |
| **用指标反过来否定根因判断** | 根因修了但指标没动，于是回去改提示词，越改越乱 | 分清"前置条件"和"指标杠杆"，两者都要做 |
| **只留摘要不留原始输出** | 诊断时无从下手 | 探针保留完整回复 + 工具参数 |

## 九、可复用的检查清单

**开始优化前**：
- [ ] 判据是用户能感知的结果（不是工具名/节点名）
- [ ] 判据分「好/坏」两类，坏信号单独统计
- [ ] 有可重复的固定脚本（连成一条链）
- [ ] **探针自检过了**（状态跨轮 ✓、工具调用抓得到 ✓、字段/事件名来自代码 ✓）

**定位问题时**（四层依次查）：
- [ ] 状态层：模型这一刻看得到它需要的信息吗？
- [ ] 契约层：工具的返回/契约能到达**写回复的那个环节**吗？
- [ ] 路由层：该调的工具被别的规则抢走了吗？
- [ ] 工具面层：这个工具在这一刻**是否根本不该出现**？

**动手修时**（四级阶梯）：
- [ ] 先试提示词（便宜，但别指望它）
- [ ] 再试工具返回值契约（能结构化到达）
- [ ] 再试代码守卫（确定性覆盖）
- [ ] 最后考虑改结构/工具面（最贵、最可靠）

**收尾时**：
- [ ] 跑多轮确认一致性（不是单轮）
- [ ] 把结论写成测试，测试名就是结论
- [ ] 长期代价写成测试或显式登记
