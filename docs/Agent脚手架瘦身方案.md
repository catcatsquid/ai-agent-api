### 踩到的坑：L1 的假设只对了一半（重要）

L1 的原假设是"描述里的枚举会被当成规章，所以要把枚举删掉"。**删掉之后行为反而退化了**：

```
学生发「1.D 2.B 3.D 4.A 5.C」（完全规范的作答）→ 模型不调 grade_answers，反而要求：
  「请按照以下格式提交答案：题号. 知识点 + 答案」
  「规范题号的格式是：题号 + 知识点 + 图片，格式如下：…」
```

它把**出题列表的展示格式**（题号 + 知识点 + 图片）当成了**作答格式**。

原因：删掉枚举之后，模型手里只剩一个格式信号（题目怎么展示的），
而**没有任何关于"学生答案长什么样"的信号**，那个真空就被展示格式填上了。

所以正确的做法不是"删枚举"，而是**把枚举改写成"举例而非穷尽"**：

```
学生发来的内容只要像作答就原文照传，例如「1.A 2.B」「ABCDA」「AAAAA」
「全都选A」「第一题C」「对错对错」—— **这是举例，不是穷尽**，凡是作答写法都交给工具去解析。
```

同时把"答案怎么写都行"写进 `reply_text`（发给学生的那段话）——
这样既给了模型关于作答格式的明确信号，也直接告诉学生**不用照展示格式提交**，
一举解决"模型要求格式"和"学生以为必须照格式"两个问题。

> **教训（已并入检查表第 2 条）**：
> schema 里的举例要显式标注"举例而非穷尽"。
> **删掉例子不等于放宽** —— 没有例子时模型会自己发明规矩，往往比原来的例子更严。

### 踩到的第二个坑：差点把"测试脚本的 bug"当成"代码回归"（重要）

上面那个"模型要求按 题号+知识点 提交答案"的现象，我一度判定为 L1 造成的回归。
**它是我的探针脚本自己的 bug。**

```python
CASES = [("规范题号", "1.D 2.B 3.D 4.A 5.C"), ...]   # (标签, 作答文本)

for text, label in CASES:        # ← 变量接反了！
    ... process_message(sess, text)   # 发出去的是"规范题号"这四个字
```

于是脚本实际发给模型的是「规范题号」—— 模型一本正经地解释
"规范题号的格式是：题号 + 知识点"，看起来**完全像**"模型在刁难学生格式"。
同理「纯字母」→ 模型回"不要使用纯字母回答"。

而同一时期另一个写对了的 A/B 脚本（`ab_grade_description.py`）三个变体都是
转发 3/3 —— **那个正确的信号被我忽略了**，因为我更相信自己刚"读到"的现象。

修正变量顺序后重测（`debug/probe_answer_forwarding.py`）：
**12 次全部转发成功，0 次要求格式。**

**方法论教训（比技术结论更值得记）**：

1. **观察到的"模型退化"，先怀疑观测工具**。探针脚本、断言条件、会话构造
   都可能是错的那一方。本次如果没写第二个独立诊断去交叉验证，
   就会基于假信号去改代码（我确实已经改了）。
2. **两个独立探针结论冲突时，优先信"写得更简单、变量更少"的那个** ——
   本次正确的那份脚本恰好也是最简单的（只有 `set_desc` 一个变量）。
3. **给探针加"自证"字段**：把"我到底发出去了什么"打出来
   （本次加上 `回复: …` 与 `工具: …` 才看出模型在回答关于"规范题号"的问题）。
4. **别用被测对象自己的术语当测试输入**。用「规范题号」这种像元语言描述的字符串
   做输入，本身就会诱导模型讨论格式 —— 输入应该是真实学生会打的东西。

## 一、问题陈述

LLM 助教每轮对话，模型上下文的固定部分是：

```
SYSTEM_PROMPT（人设 + 工作习惯）      488 字符  ≈  244 tokens
工具定义（8 个工具的 schema）        3667 字符  ≈ 1833 tokens
─────────────────────────────────────────────────────────
固定开销合计                        4155 字符  ≈ 2077 tokens

用户这句话「我不会」= 3 字符 = 固定开销的 0.07%
```

固定开销本身不是纯粹的浪费（它承载了能力与契约），但有两个代价：

1. **注意力被稀释**：模型在"我该调哪个工具、契约要求什么"的框架里思考，
   而不是在"这个学生在卡在哪里"的框架里思考；
2. **描述写成枚举 → 反而收窄行为**：`grade_answers` 的描述列了 3 种答案格式，
   模型就把 `AAAAA` 判成"非法输入"拒绝掉（这就是"契约冲突"那条机制）。
   —— 但注意：这一点在阶段 1 被证明**只对了一半**，见上面「踩到的坑」。

所以瘦身不只是省 token，**更是减少"规章感"**。

## 三、优化项（按"收益 / 风险"排序）

### L1. 把"呈现契约"从 schema 搬到返回值 —— **双赢，优先做**

**原理**：schema 说"是什么"，返回值说"怎么用"。现在两边重复，而 schema 那一份会变成规章。

| 工具 | 现在描述里有什么 | 应该只留什么 |
|------|-----------------|-------------|
| `grade_answers` | 格式枚举清单（262 字符）→ **正是它导致 AAAAA 被拒** | "像作答就原样传，格式由工具解析；解析不了会告诉你"（约 80 字符） |
| `get_paper_questions` | 分组规则 + 展示要求（236 字符） | "取一组题"（约 60 字符）；分组/展示细节都在返回值的 `reply_text` / `_guide` 里 |
| `prepare_custom_quiz` | 适用场景说明（142 字符） | "取临时出题的素材"（约 70 字符） |
| `explain_question` | 调用时机说明（102 字符） | "取题面与参考答案用于讲题"（约 60 字符） |

预期：描述 873 → 约 270 字符，**省约 600 字符**，并且**消除"枚举被当规章"这个失效模式**。

> 注意这不是"删信息" —— 这些信息会以 `_guide` 形式出现在工具**返回值**里，
> 时机更准（就在该用的时候出现），也不会被当成全局规章。

### L2. 合并/剔除练习统计工具 —— 省 439 字符 + 2 个决策点

三个选项：

| 方案 | schema 变化 | 说明 |
|------|------------|------|
| (a) 合并成一个 `practice_stats(action="get"\|"record")` | 439 → 约 230（省 210） | 保留能力，参数化 |
| (b) **直接删掉两个工具** | 439 → 0（省 439） | **推荐**：功能从未被调用、没有 UI、没有消费方 |
| (c) 保持现状 | 0 | 保留"以后可能要做"的想象 |

推荐 **(b)**，理由：**没有需求驱动的能力就是负债** —— 它既占 schema、又占模型的决策面
（8 个工具里 2 个是死的，模型每次都要多排除两个）。实现代码只有 23 行，
将来真要做练习统计，加回来成本极低。

> 这条需要你拍板：README 的工具表里列了"练习次数统计"，
> 删掉的话我会同步更新 README 和 `docs/案例-手写助教的完整生命周期.md`。

### L3. 压缩 `prepare_custom_quiz` 的参数（5 → 2）

现在 5 个参数（`topic` / `course` / `qtype` / `count` / `difficulty`），参数 schema 387 字符。

改成：

```
topic   (string, 必填)  知识点或章节，如「死锁」「TCP拥塞控制」
request (string, 选填)  其他要求，自然语言，如「5 道选择题，进阶难度」
```

理由：出题本来就是模型自己写，那 4 个参数只是给它的提示，用自由文本一样能表达，
而且**更灵活**（学生说"来 3 道送分题"这种，结构化参数反而表达不了）。

预期：387 → 约 150，**省约 240 字符**。

### L4. `explain_question` 去掉 `qids` 参数（保留实现支持）

现在 `no`（题号数组）和 `qids`（qid 数组）都能指定题目。模型只需要一个入口。

- schema 只留 `no`；
- 实现里**继续支持** `qids`（向后兼容、也方便手写调用），只是不告诉模型。

预期：301 → 约 200，**省约 100 字符**。

### L5. `search_knowledge_base` 去掉 `chapter` 和 `top_k`

现在 4 个参数（316 字符）。`course` 有用（防串味），另外两个：

- `top_k`：默认 5 就够，模型几乎不需要调；去掉后由代码固定。
- `chapter`：有了按课程的 `sources` 过滤后基本冗余；而且学生说"第 5 章"时，
  模型用 `query` 带上"死锁"这类关键词效果一样。

预期：316 → 约 150，**省约 166 字符**。

### 汇总预期

| 项 | 省下（字符） | 工具数变化 |
|----|-------------|-----------|
| L1 描述搬家 | ~600 | — |
| L2 删练习统计 | ~439 | 8 → 6 |
| L3 压自拟题参数 | ~240 | — |
| L4 去 qids | ~100 | — |
| L5 去 chapter/top_k | ~166 | — |
| **合计** | **~1545** | **8 → 6** |

```

      → 约 2610 字符 ≈ 1305 tokens   （-37%）

工具数：8 → 6（模型每轮的决策面缩小 25%）
SYSTEM_PROMPT：488 字符，**不动**（人设与能力说明是防退化的，收益低风险高）
```

## 四、明确**不做**的方案（以及为什么）

这一节和方案本身同样重要 —— 有些"看起来能瘦身"的做法方向是错的。

| 方案 | 为什么不做 |
|------|-----------|
| **按会话阶段动态加载工具子集**（比如刚开始只给 `list_papers`，进刷题后再给批改工具） | **直接违反"信息完备性"**。学生可能在任何时刻说"另外出几道题"，此时模型若看不到 `prepare_custom_quiz` 就只能拒绝或瞎编。本次所有有效修复都是**反方向**（把能力显性化，例如新增 `explain_question`）。这是最诱人也最危险的一条。 |
| **削减 SYSTEM_PROMPT** | 488 字符本身已经很短，而它承载"学生说不会要真的教"这类防退化说明。风险大于收益。 |
| **用规则/正则替代工具**（例如用正则判"学生是不是在提交答案"） | 这就是"契约冲突"那条机制的根源。用户说法千变万化，正则一定会误判。 |
| **把 `reply_text` 挪回 schema 当"格式要求"** | `reply_text` 的价值恰恰在于它是**数据**（成品文本）而不是**要求**。挪回去就退化成规章。 |

## 六、验证方法（怎么证明"更灵活"而不是"更糟"）

| 指标 | 怎么测 | 期望方向 |
