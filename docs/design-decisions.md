## 一、两条 Agent 路径：为什么留、为什么不对外

| | LangGraph（Plan-and-Execute / ReAct） | 手写循环（`frozen/tutor_agent.py`） |
|---|---|---|
| 定位 | **产品主路径**，唯一有 HTTP 入口的实现 | **冻结的对照实现**，只保留模块与测试 |
| 业务逻辑 | `course_agent/quiz_service.py`（同一份） | 同上，只包了不同的外壳 |
| 刷题主流程 | 跨轮游标 / 自拟题 / 讲题 都齐 | 齐 |
| 会话守卫 | 无（没有"没看到题目"重发、没有一次性纠偏） | 有 |
| 上下文治理 | 摘要压缩（`memory.py`） | 摘要 + 工具结果压缩 + 历史裁剪 |

**两条路径的业务逻辑已合并到 `quiz_service.py` 一份实现**，各自只保留"外壳"
（一边返回 JSON + 显式参数，一边返回 dict + 会话游标 + `_guide`），所以维护成本不是双份。

需要如实说明两点：

1. 手写这条最初兼着**对照实验**的目的 —— 跟"Python 状态机版学习/复习模式"比一比
   "LLM 主导是不是更灵活"。这个对照**没有做完**：另一半（LangGraph 版助教 `lg_tutor.py`）从未实现，
   而状态机版（`learn.py` / `review.py`）已被它取代并删除。
2. 它**不是按路线周次做的**，也**不从界面进入** —— 界面上已撤掉模式切换，日常只有 BOT 一条产品路径。
   撤掉界面入口的直接原因：两条实现经同题对比后**能力已等价**
   （同一段学生脚本 5 个场景：**16 好/3 坏 vs 18 好/2 坏**），
   留两个入口只增加"该用哪个"的困惑，而每加一个能力维护两遍是真实成本。

**现在由测试拦着**：`tests/test_route_surface.py` 的路由清单 +
`tests/test_tutor_reference.py::TestTutorHasNoHttpOrFrontendSurface` —— 想加回 HTTP 面必须显式改测试。

> 面试怎么讲：不要把它讲成"我做了两个版本"，讲成
> **"我做了一次等价性验证，然后主动删掉了一个入口，并用测试把这个决定固化下来"**。

## 二、Plan 图曾经在刷题流程上是坏的

**现象**：会编造题目和图片链接。
**根因**：它**主动丢弃工具结果**，导致跨轮状态无处安放 —— 上一轮出的题、题图、游标全没了，
模型只能凭上下文猜，猜不出来就编。

这是"状态放在哪"这个架构问题的典型症状，不是 prompt 能修的。修法是把工具结果的**最小必要部分**
显式放进 state（而非塞进 messages 让模型自己找），并让出题接口的返回值**本身**不含题干与答案。

顺带产出：`no_stem_leak` / `images_all_from_bank` 这两条评测判据 —— 都是从这个 bug 反推出来的。

## 三、题库"只加载到 125/191"事件

题库一度是 191 题 / 8 份卷子。当时的加载入口同时读一个**过期快照** `question_bank.json`（只有 125 题）
和 6 个单卷文件，并且快照"长得像全部题库"，于是少了 2019 计网期末 50 题 + 2018 OS WuuTang 16 题。

**处理**：删除过期快照，`qbank.py` 只扫描 `data/question_bank/questions_*.json` 并去重合并，
`/qb/list` 里的"全部题库（合并）"改为虚拟条目。
**代价**：人工筛掉了那两份卷子（共 66 题）及只被它们引用的 66 张题图，所以现在 125 题 / 6 份卷子。

图片也清理过两轮：292 → 191（删试卷改名留下的孤儿图 101 张 / 46 MB）→ 125。
现在"文件数 == 引用数"，由 `tests/test_qbank.py` 守着。

> 这是"**单一数据源**"最好讲的一个案例：两个来源长得像同一份数据，就是 bug 的温床。

## 四、逐字流式在生产里从未生效（v1.7.1 → v1.7.2）

见 README「最值得看的三个设计」第 1 条。补充三条根因链：

1. `SimpleLLM` 只实现 `invoke` / `bind_tools`，不是 LangChain ChatModel；
   `stream_mode="messages"` 只认实现了 `_stream` 的 Runnable
2. 640+ 项测试没抓到：流式用例用的是 `GenericFakeChatModel`（真 ChatModel，自带 `_stream`），**从没跑过生产对象**
3. 前端有 `done.answer` 兜底，所以"能用，只是慢 33 秒" —— **兜底掩盖了缺陷**

**修完之后的两条纪律**：
- `tests/test_llm_streaming.py` 只对**生产那个 `llm` 对象**下判据（用假 HTTP 层），并做变异验证
- 每条评测用例必须有"最低门槛"判据（`answer_min_chars` / `require_streaming`），
  否则空回答会让所有"不许出现 X"的判据**真空通过**

## 五、评测判据的改动记录（改判据必须留痕）

| 版本 | 改动 | 理由 |
|---|---|---|
| 1.7.2 | `max_ttft_ms` 8000 → 15000 | 8 秒是"流式完全没生效"时写的。p50≈6.5 秒后，8000 变成**边界误报**（实测 8250 / 8656 / 9170 ms 都判红）。它要挡的是"30 秒以上才出字"，门槛仍在 |
| 1.7.2 | `dont_know_calls_explain` 第 2 轮 `answer_min_chars` 80 → 40 | 讲一道题的思路本来就可能 57 字；80 字是在拿字数当质量 |
| 1.7.2 | 新增 `no_internal_artifacts` | planner 计划 JSON、`search_knowledge` 的使用说明不许进正文；讲解类用例没有真值可比，所以它不比对真值 |
| 1.7.3 | 新增 `react_no_tool_call_leak` | ReAct 图上从没用过"正文里没有工具调用原文"这条判据，顺带抓到"模型只嘴上说要调工具" |
| 待发布 | `require_streaming` 加"出题轮例外"：这一轮调了 `QUIZ_TOOLS` 之一时，判据反过来要求**不流式**（`content_events == 0` 且 `answer_source == "done"`） | 2026-10-18 用户实测：题库出题的正文里每条都带 `![题目](/qb_images/…%E5%B9%B4…png)` 的长 URL，逐字推会先刷出一堆半截 URL 与坏图。产品上改成"出题轮只发进度、正文 done 一次给全"。判据跟着改，否则所有出题用例都会红；而且反过来能守住"哪天又开始吐 URL" |

## 六、为什么 `docs/` 那批文档不随仓库分发

那批文档（项目总览、架构审查、缺陷报告、方法论等 18 个文件）大部分是**AI 辅助整理成稿**的：
素材来自真实排查记录，但成稿时的判断、措辞、归纳是否与本人一致，需要逐篇过一遍。
在核实完成之前，不适合把一个"自己还没完全背书"的版本当项目说明对外分发。

结论：**代码与测试是唯一权威**。文档说法与代码/测试冲突时，以代码和测试为准。
