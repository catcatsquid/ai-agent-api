## 本轮修复记录（安全 + 成本 + 泄题 + 架构去重）

### 第六轮：学习/复习模式（新功能）—— 以及它返工四次教的东西

**用户需求**：说"我要复习某门课/某个章节"时**分节**过一遍、**优先参考 PPT**；
说"我要学某门课的某章"时仔细讲那一章。并且明确要求：
**不要把"一节几个知识点"写死**（分节由模型判断）、**不要死板 prompt、不要状态机**。

**设计**（按本项目一贯的原则：结构与契约放工具返回值，判断留给模型）：

| 工具 | 角色 | 为什么这样设计 |
|---|---|---|
| `list_course_sections(course)` | **素材地图** | 分节的依据必须来自真实资料：**PPT 文件名本身就是分节结构**（`02-1-进程与线程之进程.pdf` / `05-死锁.pdf`），`chunk_count`≈内容量供模型判断"一节讲多少"。刻意**不给**固定切分 |
| `read_section(course, chapter?, section?, offset?)` | **按课件原始顺序读** | 讲一章要的是"这章按顺序讲了什么"，不是"最相似的几句"（那是 `search_knowledge` 的活）。分页读，读多少由模型判断 |
| `record_study_position(...)` | **书签**（不是状态机） | 只记"学到哪了"，流程仍由模型决定 |
| `search_knowledge(query, course?, source?)` | 限定范围检索 | "优先 PPT""不串课"做成**检索过滤器**，而不是 prompt 里的一句请求 |

**返工四次，每次都暴露一个真问题**（这段比结果更值得记）：

1. **光在提示词里写"优先课件"没用。** 实测模型照样去读了《操作系统_补充知识点笔记.md》，
   还在回复里**谎称**"以下是《05-死锁.pdf》的内容"。
   → 把纠偏**搬进工具返回值**：读到课本/笔记就**自动换成课件**并说明。
2. **"自动换"也翻车了：模型编文件名。** 它调 `read_section(source="操作系统课件")`
   —— 这个名字不存在；拿不到资料后**退回凭记忆讲**（"OS是管理硬件和软件资源的系统软件"）。
   → 不再让模型叫文件名，改成 **`course` + `section` 编号**，材料由工具认。
3. **只做"第几节"又丢了"按章名找"。** 而学生最自然的说法正是"我要学**死锁那一章**"；
   模型于是读了第 1 份课件，还谎称讲的是死锁。
   → 补 `chapter` 参数，按章名定位（含"找不到时列出可用章名"）。
4. **"继续讲"它记不住"读到哪了"。** 返回值里明明写着"下次用 offset=15 继续"，
   它还是跳去读下一份课件、然后说"课程材料没覆盖这个内容"。
   → ① 把"读到哪了"**自动记进会话状态**（工具返回里加一行机器可读的 `[study-state]`）；
     ② planner 侧注入一句**可直接照抄的调用** —— 描述式提示它不跟，照抄它就跟。

> **第一版还踩了一个隐蔽的坑**：我按自然语言措辞解析 `read_section` 的返回值来存位置，
> 结果 `study` 里**没有 course**；而 planner 是 `if study.get("course")` 才注入"当前位置"，
> 于是整块提示被静默跳过 —— 看起来"记了"，实际没传给模型。
> 是 `runtime/plan_cursors.json` 的内容把它暴露出来的。
> **修法：工具显式输出机器可读的一行，别再解析人话。**

**能复用的三条**：
- 想让模型"优先用某种材料"，就把它变成**检索/取数的过滤器或默认值**，不要写成请求；
- 不要让模型**叫出资源名**（它会编）；让它给**有限集合里的编号/名称**，由工具解析；
- 需要跨轮记住的东西，**别指望返回值里的一句话** —— 交给状态，并且**用结构化的行**解析。

**实测（打真实服务，三个回合）**：
```
「我要学操作系统的死锁那一章」→ list_course_sections + read_section(按章定位→05-死锁.pdf) → 讲课件原文 ✅
「继续讲」                   → read_section(05-死锁.pdf, offset=15) 第16~30块 → 讲银行家算法 ✅
「我懂了，下一节」            → record_study_position + read_section(下一份课件) ✅
```
测试：`tests/test_study_mode.py` 51 项（含 6 项章名定位、参数容错、书签与游标互不干扰、
prompt 契约、以及"工具必须给机器可读行"的回归）。

### 第五轮：「导出对话」一直在骗用户（实测发现）

**用户报告**：点了 BOT 的「📥 导出当前对话」，提示"已导出"，但**找不到文件**。

**先查磁盘**：`%USERPROFILE%\Downloads` 里 **0 个文件**、近 30 分钟没有任何新文件
→ **下载根本没发生**，是提示在说谎。

原实现只有浏览器下载，而且：

```js
a.click();
URL.revokeObjectURL(url);          // ← 缺陷1
showToast('对话已导出', 'success'); // ← 缺陷2
```

1. **`revokeObjectURL` 紧跟 `click()`** —— 下载还没解析这个 blob URL 就把它释放了，
   下载会被**静默取消**（小文件不一定复现，所以更难发现）。
2. **提示无条件报成功** —— 下载是异步的，还可能被浏览器 / iframe 的 sandbox 拦掉，
   前端**根本无从得知**结果，却告诉用户"已导出"。

**修法：让结果可验证。** 加 `POST /chat/export`，**先在服务端落盘**到 `exports/`
（这一步的成败前端一定拿得到），返回**真实路径**并显示在提示里；
浏览器下载降级为"顺带触发一下"，失败也不影响结果。

**测试还抓到第三个 bug**：文件名时间戳只到**秒**，
同一秒内导出两次会算出同一个文件名 → **后一次静默覆盖前一次**。
（`test_two_exports_do_not_overwrite` 第一次跑就红了，日志里两次是同一个文件名。）
已改为撞名就往后加序号。

**通用教训**（都可以迁移到别处）：

> **凡是"提示成功"的地方，都要能拿到真实的成败。**
> 前端做 `Blob` 下载时拿不到，所以要么换一条可验证的路径（服务端落盘），
> 要么就不要报成功。**"看起来成功"比"明确失败"危害大得多** ——
> 用户会以为文件在某个地方，而实际上什么都没发生。

**验证**：`tests/test_chat_export.py`（9 项，含 3 项读真实 HTML 的前端守卫：
禁止紧跟 click 就 revoke、必须调服务端接口、失败必须报错）+ 打真实服务 7 项检查。

**顺手挖出的一个更重要的问题**：`data/` 下**曾经 0 个文件被 git 跟踪** ——
题库 JSON 虽未被 ignore，但**从来没被 `git add` 过**。也就是**别人 clone 下来跑不了测试**，
而"没有 CI"掩盖了这件事。

处理方式：
- 把题库 JSON（361 KB，8 份卷子）纳入版本控制 —— 它本来就是测试的 fixture，
  `.gitignore` 里作者写的 `!data/question_bank/*.json` 也表达了同样意图；
- `tests/conftest.py` **集中声明每份数据集的可用性**：缺数据的用例**跳过**（不是报红），
  并在测试开头打印 `数据集: question_bank=有, images=有, vector_store=有`。
  实测把题库挪走后跑：**147 通过 / 258 跳过 / 0 失败**（而不是一片红）。

> **这条经验值得记**：测试对"本地大文件"的隐式依赖，会让 CI 变成摆设 ——
> 要么把 fixture 纳入版本控制，要么让缺失变成**显式跳过**。
> 让"数据没带"看起来像"代码坏了"，是最容易骗到自己的一种失败。

### 第三轮：Plan 模式在刷题流程上是坏的（实测发现）

> **这是本项目最有价值的一个发现之一**：同一个 Agent 系统里，
> **"工具结果要不要留在上下文里"这一个设计选择，决定了多轮会话能不能成立。**

**实测（`debug/live_plan_quiz_flow.py`，打真实服务）**：

| 场景 | Plan-and-Execute | ReAct |
|---|---|---|
| "我想刷计算机网络的选择题" | ❌ **伪造题目** + 编出 `https://example.com/net1.jpg` 假图 | ✅ 真图片（`/qb_images/...`） |
| "继续下一组" | ⚠️ 游标时好时坏（见下） | ✅ 正确给出第 2 组 |
| "第1题我不会" | ❌ 不调 `explain_question`，泛泛谈知识点 | ✅ 调了，并引用**真实题干与答案**（已核对 `2019网期末_Q13`） |
| "另外出几道题" | ❌ `prepare_custom_quiz` **根本没注册** | ⚠️ 有工具 |
| 正文 | ❌ 漏出 `get_paper_questions {"paper_source": ...}` 原文 | ✅ 干净 |

**机制（关键）**：

```
ReAct 的 llm_node：把 state["messages"] 整段给模型（含 ToolMessage）
   → 上一轮工具结果里的 next_group_index 留在"带内"，模型看得见  ✅

Plan 的 planner_node（nodes.py:146-159）：主动排除 ToolMessage
   + assistant 内容只保留前 200 字
   → 卷子和组号全丢；而 AgentState 只有 {messages, plan, tool_rounds}
   → 跨轮状态无处安放  ❌
```

**根因不止一个**：
1. `PLANNER_PROMPT` **把 `get_paper_questions` 描述成"获取指定试卷的所有题目"**
   —— 实际一次只给一组，而且**完全没提 `group_index`**。planner 的预期一开始就是错的。
2. 工具清单写着"你有 8 个工具"，实际注册 9 个；`explain_question` 注册了却
   **既不在 prompt 里、也不在 `has_paper_tools` 白名单里** → 讲题路径不可能被规划出来。
3. 该路径的工具**只返回"数据"，没有任何"该怎么呈现"的指引** ——
   synthesizer 手里没有工具、又想满足用户，于是**自己编题**。
4. Plan 图是**单向**的（planner → executor → synthesizer），synthesizer **没有能力再取数据**；
   一轮规划不够时它只能编，或者把工具调用**当正文写出来**（实测漏过 JSON 原文）。

**这一轮修了什么（止血，已实测验证）**：

| 改动 | 效果 |
|---|---|
| `PLANNER_PROMPT`：修正 `get_paper_questions` 描述、补 `group_index`/`next_group_index`、工具数 8→9、补 `explain_question` 及其触发条件 | `explain_question` **现在会被调用了** |
| `has_paper_tools` 白名单补 `explain_question` | 讲题不再被误判为"检索不足"而多跑一次联网搜索 |
| 两个 prompt 加**"不许编题"**硬规则（点名禁止占位图片地址、禁止把工具调用写进正文） | 减少但不能根除 |
| **给 Plan 路径的工具补上"呈现契约"**：`list_papers` 返回里带"本步只做一件事：只列清单，不要开始出题"；`get_paper_questions` 返回 `reply_text` + `render_hint` | **伪造题目被修掉了** ✅（实测第 1 轮现在如实列卷子并问选哪份，第 2 轮给真图片） |

**还没修（属于"路线 A"的工作）**：
- **跨轮游标**：Plan 模式下"继续下一组"**时好时坏** —— 因为 `reply_text` 里带着
  "第 1/19 组"这种文字，模型**有时能从自己上一轮发出去的话里推断出该取第 2 组**，
  有时推不出来。**间歇性错误比稳定错误更难信任。**
  正解：给 `AgentState` 加会话/游标字段（ReAct 靠"工具结果留在上下文"天然解决）。
- **synthesizer 无法再取数据**：一轮规划不够时它只能编或写假调用。
  正解：让 synthesizer 也能触发一次工具调用，或者把 Plan 图改成允许有限次 re-plan。

> **顺带纠正我自己的一个说法**：我之前讲"两个运行面有意保留对照" —— 实测下来这个说法站不住。
> Plan 模式不是"另一种选择"，它在刷题流程上确实是**坏的**。这是个缺陷，不是设计。

**验证**：

```bash
.venv/Scripts/python.exe -m pytest tests/ -q                       # 382 项
.venv/Scripts/python.exe debug/live_plan_quiz_flow.py              # Plan 模式刷题流程实测
.venv/Scripts/python.exe debug/live_react_quiz_flow.py             # ReAct 对照
.venv/Scripts/python.exe debug/probe_quiz_on_langgraph.py          # 工具/prompt/状态一致性
```

新增守卫测试 `tests/test_planner_prompt_contract.py`（13 项）用**一致性断言**守住这类问题：
"注册了的工具必须出现在 prompt 里"、"prompt 声明的工具数必须等于实际注册数"、
"白名单必须覆盖所有刷题工具"、"不能把 `get_paper_questions` 说成取整卷"。
**这类 bug 的根源是"加工具时忘了改 prompt"，用枚举式断言才挡得住。**

### 第一轮：安全 + 成本 + 泄题（7 项）

| 条目 | 问题 | 修法 |

面试时最好主动把这个特征说清楚（为什么两套、各自换来了什么），

## 二、框架级问题

### 2.1 Agent 编排与运行时

#### F1【架构级】两套 Agent 实现并存，职责重叠

| | 模式 A 知识寻回BOT | 模式 B LLM 助教 |
|---|---|---|
| 编排 | LangGraph `StateGraph`（planner→executor→synthesizer / ReAct） | 手写 `while` 循环（`process_message`） |
| 状态 | `MemorySaver` + thread_id | 进程内 `_SESSIONS` + session_id |
| 工具 | `tools.py`，LangChain `@tool` | 内联 schema + `TOOL_HANDLERS` |
| 流式 | 节点事件 + token | 自己解析 SSE 增量、拼 `tool_calls` 分片 |
| 上下文治理 | `memory.py`：窗口 + LLM 摘要 | `_compact_tools` + `_trim_history` |

**实测重复代价**：`tutor_agent.py` 1251 行里约 **329 行（28%）** 是 LangGraph 白送的管线
（会话管理、流式解析、tool_call 拼装、上下文压缩、主循环）。

**真实危害**：同一能力两份包装，**修一份忘另一份**。
证据：`get_paper_questions` 的"翻组"能力，`tutor_agent.py` 那边有会话游标，
`tools.py` 那边曾长期把 `group_index` 硬编码为 1，文档却写"取下一组" —— 典型双份漂移。

#### F2【严重】会话状态有两份，都是进程内存，都没有上限

| 存储 | 位置 | 持久化 | 淘汰 | 多 worker |
|---|---|---|---|---|
| `MemorySaver`（模式 A） | `graph.py:37` 模块级单例 | 无 | **无 TTL / 无上限** | 不共享 |
| `_SESSIONS`（模式 B） | `tutor_agent.py:987` | 无 | 有（3 小时） | 不共享 |

实测：`MemorySaver` 实际类型是 `InMemorySaver`，构造参数无 TTL；
LangGraph 每执行一个超步就写一个 checkpoint → **长跑内存单调增长**。

影响（面试常问的"生产化"）：重启丢会话；`--workers 4` 时同一用户请求落到不同 worker 直接断上下文；
与 README"第 8 周完成 Docker 部署"形成落差，需要主动说明边界。

#### F3【严重·已复现】两个图共用同一 checkpointer，且前端不重置 thread_id

`graph.py` 里 `graph` 与 `react_graph` **都** `compile(checkpointer=memory)`（同一实例）。实测：

```
往 graph 写 thread_id="probe-shared-thread" 的会话（2 条消息 + plan 字段）
→ react_graph.get_state(同一 thread_id) 读到了对方的 2 条消息，连 plan 字段一起读到
```

而前端 `setReasoningMode()` **不重置** `currentThreadId`（`setAppMode()` 才重置）。
所以"先 Plan 对话，再点 ReAct 继续发消息"这条**真实可操作路径**下，ReAct 从 Plan 的 checkpoint 继续。

**后果比"读到对方消息"更严重（已复现）**：Plan 图的 executor 会造出合成
`ToolMessage(tool_call_id="plan_0")`，而 state 里**没有任何 assistant 消息声明过 `plan_0`**。
切到 ReAct 后，llm_node 发出的 payload 里就带了一条**没有对应声明的 tool 消息**
→ OpenAI 兼容接口按协议拒绝（400）→ 被 `safe_llm_invoke` 吞掉，降级成兜底话术。
也就是说：**混用模式会让模型静默退化成只会说套话**，而不是报错。

**最小修法**：前端切模式时重置 thread_id；或两个图各用独立 checkpointer
（更彻底：executor 不要造合成 `tool_call_id`，工具结果走独立 state 字段）。

#### F4【中】工具层双份实现（与 F1 同源）

- `_grade_with_llm` 在 `tutor_agent.py` 与 `tools.py` **各一份**；
- `list_papers` / `get_paper_questions` / `grade_answers` / `explain_question`
  在 `tools.py`（LangChain 包装）与 `tutor_agent.py`（原生 schema 包装）**各一套**。

共用的只有 `qbank.py`（这点做得对）。但包装层重复意味着参数语义、校验、错误文案都要维护两遍。

#### F5【中】巨型模块：5 个文件 > 700 行

```

部分覆盖：`nodes.py`（借 `test_memory.py` 两个接线测试）、`server.py`（借 `test_auth.py` 的
`/health`、`/auth/login`）、`ppt_processor`（借 `test_image_understanding.py` 的 3 个冒烟）。

**几乎没有专门测试**，而手写那条有 71 项。测试重心与主路径不一致。

另外 `tests/test_qbank.py` 直接断言 `len(qs)==191`，绑死磁盘数据 —— 内容一动就红，

>
> ```
> 加载结果必须覆盖所有 questions_*.json 里的每一道题（按 source+qid 比对）
> ```
>
> 并给另一处同源的硬编码 `== 191`（我在 `/qb/search` 修复时自己写的）也换成了
> "两个入口必须一致"。**这是本项目里"不要断言数据快照、要断言不变量"最直接的一次教训** ——
> 而且它证明了：审查时写下的预警，比事后解释有价值得多。

#### F7【中】Agent 决策层几乎没有日志（trace_id 机制空转）

`logger.py` 的设计是对的：`ColorFormatter` 从 `contextvars` 自动取 trace_id，
任何 `logger.*` 调用都自动带上，**不需要手动打点**。但实测各模块日志调用数：

```
rag_tool.py                1249 行   28 次
course_agent/server.py      735 行    2 次
course_agent/nodes.py       457 行    1 次
course_agent/tutor_agent.py 1251 行   1 次
```

**请求级有日志、知识库内部有日志，但"Agent 为什么这么决策"完全没有日志。**
面试官问"线上一次回答错了你怎么排查" —— 目前只能看到 `POST /qa/stream 200` 和检索日志，
看不到 planner 生成了什么计划、工具怎么被调、上下文压缩掉了什么。

#### F8【严重·已复现·✅已修复】ReAct 工具环**没有业务级轮数上限**，靠框架默认的 10007

`should_continue`（`nodes.py:452-457`）只判断"最后一条消息有没有 tool_calls"，
`tool_node`（`:429-449`）也不计数 —— 也就是说**循环次数完全由模型自己决定**，
真正的上限是 LangGraph 默认的 `recursion_limit=10007`。

实测（mock LLM 每轮都返回 tool_call）：抛错前真实发生 **LLM 调用 5004 次、
工具调用 5003 次、耗时 150 秒**。

对照：手写的 `tutor_agent.py:1064` 有 `_MAX_TOOL_ROUNDS = 6`。
**这条很有说服力 —— 手写那条在这个维度上比框架那条更安全。**

#### F9【架构级·已复现】同一 thread_id 并发请求会**静默丢掉一轮**

`InMemorySaver` 内部没有任何锁（读过源码确认无 `threading.Lock`）。
实测：串行 2 次 → state 里有 2 条 `HumanMessage`；
**并发 2 次 → 只剩 1 条**，另一个请求的整轮在 state 里彻底消失，而 HTTP 仍返回 200。

#### F10【架构级】Plan 图没有"会话游标"的容身之处 → 出题游标跨轮必丢

`nodes.py:146-149`（planner 组装历史时**排除 ToolMessage**）、
`:375-379`（synthesizer 同样）、`:159`（assistant 内容只保留 **200 字**）。
而 `tools.py:136-148` 自己就承认"这里没有会话状态，组号必须由调用方带"。

tutor 用 `handler(args, session)` 里的 `current_qids` / `last_group` 解决了这件事
（`tutor_agent.py:458-462`、`:538-543`），而 Plan 图**无处存放**：
学生说"继续下一组"时，游标既不在历史里（ToolMessage 被丢），也不在 prompt 里
（assistant 出题内容被截到 200 字）。

#### F11【严重·已复核·✅已修复】工具产出被当作**用户可见内容**流式吐出（一条泄题通道）

`server.py:410-421` 在 `mode == "messages"` 下只跳过"带 `tool_calls` 的消息"
（本意是挡 tool-call JSON），但 **`ToolMessage` 的内容会被原样当成 `content` 事件发给前端**。

实测（stub 工具打标记）：`stream_mode="messages"` 把 ToolMessage 直接当块吐出，
落到 `{'type':'content'}`。真实运行时吐出来的是**检索原文 / 参考答案 / 批改 JSON**。

这同时打穿了"出题不泄题面与答案"的设计意图 —— 我在 tutor 那边专门把答案从工具返回值里拿掉，
**但 Plan 模式这条通道会把工具结果整段播给学生**。

**建议方向**：工具结果走独立 channel，或给消息打 `private` 标记，消费面只读 `AIMessage`。

#### F12【中】Plan 模式的工具集合有**三处不一致**，`explain_question` 基本不可能被规划

| 位置 | 内容 |
|---|---|
| `tools.py:414-424` | 注册 **9** 个工具 |
| `nodes.py:44-52`（PLANNER_PROMPT） | 只列 **8** 个 |
| `nodes.py:310-313`（`has_paper_tools` 白名单） | 漏 `explain_question` |

实测两处漏项都是 `['explain_question']` —— 而"学生说不会"恰恰要靠它。
**也就是说：plan 模式下讲题能力实质缺失。**

#### F13【中】"自适应规划层"没有重规划，且靠中文子串 + 长度阈值判断结果够不够

`nodes.py:267-274` 是中文子串标记表，`:339` 是 `len(combined) < 100` 补搜。
问题有三个：① 这是"一次规划 + 批量执行"，**没有 Plan-and-Execute 的 re-plan**；
② 标记表与 qbank 的文案强耦合（`tools.py:124`），改一句话就可能失效；
③ 区分不了"工具坏了"和"知识库为空"（`:249-252` 双重吞异常）。

实测一个具体误判：`plan=[get_course_info]`（问"知识库有多少内容"）时，
因为 `:322-326` 把"条文档分块"这类结果过滤掉了，`:328-329` 认为结果为空
→ **必然误路由到 `web_search_fallback`**，给用户追加一次无关的联网搜索。

#### F14【中】计划步数与工具串行：只有 prompt 约束，没有代码上限

`nodes.py:65` 在 prompt 里写"最多 3 个步骤"，而 `:196-218` **没有任何上限**。
实测模型返回 50 步 → 50 步全部进 executor，且**串行执行、无依赖语义**。

#### F15【中】`llm.py` 完全无日志，重试全静默

`llm.py:78-95` 对**任意异常**都 sleep 后重试 3 次（包括 JSON 解析错误、字段错误）；
全文件 **0 条 logger**（已 grep 确认）。成功调用也无记录
→ trace_id 只有请求级那一行，没有"用了哪个模型、耗时多少、解析成败、跑了哪些工具"的链路。

#### F16【中】`SimpleLLM` 不是 LangChain `Runnable`，"伪适配器"的兼容面很窄

`llm.py:103-136`。实测确认：

- `isinstance(llm, Runnable) == False`，没有 `_generate` / `with_retry`；
- `invoke` 的 `config` 参数被**直接丢弃**（`:125`）→ 无 callbacks / LangSmith / structured output；
- `astream`（`:131-136`）用**同步** `requests.post` 包 async generator，
  **且完全忽略 `_tools`** → 实测 tools=None，**工具能力静默退化为纯文本**；
- 所有节点共用硬编码 `max_tokens=2000` 与同一 temperature（`:128`）。

**加分项**：`bind_tools → invoke` 的 tools 透传是做对的（实测 9 个工具确实送达 API）。

#### F17【中】`record_practice` 是**全局有状态**工具，读-改-写无锁

`tools.py:112` 的模块级 `_STATS_FILE` + `:391-407` 的读改写。
实测：**12 个并发调用只记到 3 次**。
而且同一份 stats 文件还被 `tutor_agent.py:219` 的**另一套工具层**读写（呼应 F4 的双份实现）。

#### F18【中】兜底节点无保护查表，一处 `KeyError` 打穿整张图

`nodes.py:351` 写的是 `tools_by_name["web_search"]`，
而同一文件里 `:240` 用 `not in` 判断、`:436` 用 `.get` —— **三种风格并存**。
实测：`tools_by_name` 里缺 `web_search` 时该节点抛 `KeyError` 直接终止 invoke；
而 `executor_node` 对未知工具会优雅返回"未知工具: nope"。

#### F19【低】编排层的零散契约漂移与死引用

| 位置 | 问题 |
|---|---|
| `nodes.py:419-421` | `trim_messages(max_messages=15, keep_system=False)` 按条数切，**不断言 assistant(tool_calls)/tool 配对**；而 `memory.py` 文档说"系统消息永远保留"，这里却传 `keep_system=False` |

#### F21【架构级】循环依赖：`rag_tool` ↔ `knowledge_pipeline.pipeline`

```

影响：无法单独复用 `rag_tool`；导入顺序敏感；将来拆包必然卡住。

#### F22【架构级】反向依赖：检索底层 `rag_tool` 依赖上层 `course_agent`

```python

              from course_agent.logger import logger
```

`rag_tool` 名义上是"检索工具库"，却 import Agent 包。叠加 F21 后依赖方向更乱：
它既被上层依赖，又依赖上层和同级 pipeline。

**建议方向**：`errors`/`logger` 属基础设施，应下沉为独立顶层模块，让两边都依赖它。

#### F23【架构级】`use_pipeline=True` 只是"换文本来源"，抽出的结构在入库时被抹平

`rag_tool.py:585-595` 按 `use_pipeline` 在 loader 上分叉，之后两路**汇合到完全相同**的
`chunk_text` + embedding + `upsert` + 同一套 meta。关键损失：

```python
pipeline.py:60    PPT：走 slides_to_text(slides, merge_pages=1)，页被合并
pipeline.py:72    课本：text = "\n\n---\n\n".join(notes)，多章笔记被 join 成一个字符串
                 ↓ 然后交给同一个 chunk_text
```

实测（`debug/review_probe/probe_chunk_pipeline.py`）：
- 3 页幻灯片合并后 < 300 字 → 切成 **1 个块**；
- 5 页×170 字 → 4 块，**边界落在句中，与页边界无关**；
- 3 章笔记 → 块内出现 `'---\n\n# 第二章'`，章节边界被打散。

而 meta 只有 `source/doc_type/chapter/chunk_index/char_count`（`rag_tool.py:622-631`），
**没有 page/section**。所以做不了"只查第 3 章 / 第 12 页"。

**结论**：`use_pipeline` 的实质增量是"PPT 多段 VLM 描述""课本变笔记"两种**文本内容变化**，
不是结构升级。属架构级 —— 要修得改 `process_document` 的返回结构。

#### F24【架构级·实测】`chapter` 元数据是"文件名"，但界面把它当章节展示

这是上面那条的**存储层证据**，也是用户可见的缺陷。实测 4199 个分块：

```
不同 chapter 值总数: 19（来自 20 个来源）
chapter 为空/None 的分块: 2319 (55.2%)   ← 整本课本
「chapter 多于 1 个取值」的来源数: 0 / 20   ← 关键
```

**`chapter` 与 `source` 是 1:1 的**，即它只等于文件名（或文件名前缀），不携带任何章节信息；
而占全库 55% 的课本，其 `chapter` 直接是空。

但前端 `kb.html` 把它当章节用：
- "章节数"统计卡 = `Object.keys(s.by_chapter).length` → 实际只是"来源数"（20），**标签是错的**；
- `dist-chapter` 渲染"章节分布"，内容是无意义的文件名分布。

所以"知识库按章节组织/检索"这件事**目前是假的**：pipeline 抽出的真章节在入库时丢了（F23），
存下来的是文件名，而界面把它显示成章节。

#### F25【架构级】题库构建产物与读取层之间没有契约，靠"加载顺序巧合"成立

构建器写 17 个字段（`qid/q_num/display_num/type/course/page/image/text/answer/reference_points/
topic/sub_questions/section/source/source_file/needs_review/review_reason`），

**没有 version、没有 schema 校验、没有 CI 断言。**

（`question_bank.json` 本身只有 125 题、独有题为 0 —— 见 3.2。）

### 2.3 服务分层与 SSE 协议

#### F30【架构级】`server.py` 没有服务层，路由 = 服务 = 序列化

735 行里塞了 19 个路由 + 7 个 Pydantic 模型 + **0 个 service 对象**：

- `qa_ask`(136-189) 直接调 graph 并手写 tool_calls 聚合；
- `qb_search`(693-712) 在路由里做字符串拼接 + 全量过滤；
- `qb_list`(618-648) 直接 `open()` 读 JSON；`kb_page/chat_page`(464-479) 直接读 HTML；
- `get_knowledge_base()` 在 6 个 handler 里各调一次（491-556）；
- `graph` / `react_graph` 在模块顶层直接 import（26）。

**建议方向**：`routers/` + `services/` + `schemas/`，KB 与 graph 用 `Depends` 注入。

#### F31【架构级】`/qa/stream` 与 `/chat/stream` 是同一功能的双实现，且协议不同

两段各约 120 行，都有 6 个 node 分支、都把 `content[:120].replace("\n"," ")` 写了一遍
（这个摘要表达式全文出现 4 次）；`/chat/stream` 里内联 `json.dumps` 12 处，`_sse()` 一次没用。
差别：`/qa/stream` 用 values 流 + `get_state` 取终答；`/chat/stream` 用 `["updates","messages"]` 拿 token
并多发一个 `data: [DONE]`。

**证据**：前端 `chat.html:534` 只调 `/qa/stream`；`/chat/stream` 的唯一调用方是 `tests/locustfile.py:179`
—— 也就是说**真正实现了 token 流的那个接口，前端根本没用**。

#### F32【中】前端能用的流式接口拿不到 token → 退化成"进度条 + 整段答案"

`/qa/stream` 的 `node`/`done` 事件里没有增量文本（302-306 是流结束后一次性取 `messages[-1]`）；
而前端 `appendToBubble` 只在 `content`/`token` 分支触发（`chat.html:639-646`）。
所以 QA 页的观感永远是"三个点 → 整段答案突然出现"。

#### F33【架构级】SSE 事件协议没有单一事实来源，前后端各有死代码

- 前端 `chat.html:639 case 'token'` 是**永不触发**的分支：后端三个流式接口只发
  `start/node/done/error/content/phase/discard/tool`，全项目 grep 无 `"token"`；
- 反向：`/qa/stream` 从不发 `content`；
- `[DONE]` 哨兵只有 `/chat/stream:423` 发，而它是前端不用的那个接口 ——
  于是前端专门为它写的 `if (jsonStr === '[DONE]') continue`（`chat.html:561`）在真实路径上永不生效；
- `error` 事件的字段也分裂：`msg`(311) vs `content`(426) vs `msg`(451)，
  前端被迫写 `evt.msg || evt.content`(666, 669)。

**建议方向**：一份 `EventType` 枚举（或前后端共用的 schema 文件），
外加一条"后端发的事件必须在前端 switch 里有 case"的测试。

#### F34【中】流中途异常时协议不闭合，前端会把"断流"当"完成"

实测：路由 yield 一条事件后抛异常 → 客户端拿到 **HTTP 200 + `text/event-stream` + 只有第一条事件**，
没有 `error` 事件、也没有错误信封，连接直接断；全局异常处理器只留一条日志。
`/qa/stream` 自己在生成器里 try/except 才勉强闭合（308-311）。

再叠加前端**只以"字节流结束"判定成功**（`chat.html:552-577` 没有任何终态标志位）
→ 被网关截断或进程重启截断的响应，前端会显示成"完成"。

#### F35【中】`/qb/search` 与 `/qb/topics` 的数据集不一致（实测差 66 题）

`/qb/topics` 已改为走 `qbank.load_questions()`（191 题），
但 `/qb/search` 默认读 `question_bank.json`（125 题，见 F25），文件存在时不走合并兜底。

#### F36【中】`/kb/browse` 契约自相矛盾，面包屑一进子目录就点不动

`server.py:560-607`：`data.current` 是请求原样（相对路径），

### 2.4 认证与安全 ⚠️ **这一节建议优先修**

> 当前服务只绑 `127.0.0.1`（本机访问），所以下面这些**暂时不是对外可利用**的；
> 但 README 声明了 Docker 部署，一旦按常规做法把端口映射出去，就是对外可利用的。

#### F37【严重·已复核·✅已修复】`/auth/login` 不校验密码 → 任何匿名者都能换到 JWT

`server.py:116-133` 的 `password` 字段**从未被读取**。我独立复核：

```
POST /auth/login  {"username":"probe","password":"totally-wrong"}  -> HTTP 200，返回 token
POST /auth/login  {"username":"","password":""}                    -> HTTP 200
```

它无条件 `create_jwt`，也不检查 `JWT_ENABLED`。
这不只是一个孤立的鉴权漏洞 —— 它是下面 F38 那条**任意文件读取链的入口**。

#### F38【严重·已复核·✅已修复】`/kb/add` 不校验路径 → 任意文件入库，再经无鉴权的 `/kb/search` 外泄

`server.py:518-531` 把 `file_path` 原样交给 `rag_tool.add_document`；
而 `add_document`（`rag_tool.py:767-798`）只做 `Path(file_path).exists()` 检查，
**没有任何"必须在 `data/` 之下"的包含性校验**。

关键在于 `_classify_doc`（`rag_tool.py:211-235`）：路径不在 `base_dir` 之下时
它 `except (ValueError, OSError)` **退回按全路径判断**，最终 `return "notes"`
—— 于是 `data/` 之外的任意文件都被当作"笔记"收进知识库。

完整攻击链（三步，前两步我已复核）：

```
① POST /auth/login 任意用户名+任意密码      → 拿到 JWT（F37，已复核 200）
② POST /kb/add?file_path=<磁盘上任意文件>   → 以 doc_type=notes 入库
   （dir_path 版本还能直接给 C:\ 整盘扫描）
③ POST /kb/search （无鉴权，已复核 200）      → 返回 chunk 全文 = 文件内容外泄
   GET  /kb/documents（无鉴权，已复核 200）   → 列出全部已入库语料
```

**对照**：`/kb/browse`（562-569）**做对了** —— `resolve()` + `relative_to(data_root)`，
实测 `path=../../course_agent` 返回 403。说明团队知道这个模式，只是漏在了写接口上。

**建议方向**：抽一个 `resolve_within(base, user_path)` 统一校验；
`data/` 路径改成配置项；`/kb/search`、`/kb/documents` 补鉴权；`/auth/login` 真正校验凭证。

#### F39【严重·已复核·✅已修复】鉴权只覆盖 4 个路由，最贵的接口和全部读接口裸奔

我逐路由复核（不带任何凭证）：

| 需鉴权（401） | **裸奔** |
|---|---|
| `POST /qa/ask` | `POST /qa/stream`（422，已过鉴权） |
| `POST /kb/add` | `POST /chat/stream`（422）、`POST /tutor/stream`（422） |
| `POST /kb/add-directory` | `GET /kb/stats`、`GET /kb/documents`、`POST /kb/search`、`GET /kb/browse` |
| `DELETE /kb/documents/{source}` | `GET /qb/list`、`POST /qb/search`、`GET /qb/topics` |

关键点：受保护的 `/qa/ask` **前端根本不调用**；而真正在用的 `/qa/stream`
（会烧 LLM 额度）、`/kb/search`（会触发 embedding）、`/kb/documents`（列出全部语料）
全部匿名可用。**保护了没人用的，漏掉了在用的。**

**建议方向**：把 `dependencies=[Depends(any_auth)]` 挂在业务 `APIRouter` 上，
只显式放开 `/health`、`/chat`、`/kb`、`/docs` —— 从"逐个加"改成"默认拒绝"。

#### F40【严重·用户可见·✅已修复】认证两端没接上：kb.html 的导入/删除**必然 401**

当前档位 `API_KEY=''` + `JWT_SECRET` 已配置 → `any_auth` **只认 JWT**；
而 `chat.html:181-182` / `kb.html:274-275` 只会从 `localStorage.api_key` 组 `{'X-API-Key': ...}`，
两个页面都**从不调用 `/auth/login`**（也没有登录 UI 或 token 存储）。

结果：知识库管理页的"导入 / 增量导入 / 删除"三个按钮**在页面上永远失败**，
而且错误信封是 FastAPI 默认的 `{"detail": ...}`，前端只显示成 `HTTP 401`
→ 用户看到"导入失败: HTTP 401"，完全不知道要去配凭证。

#### F41【中】两套凭证都没配时 `any_auth` fail-open，且短路在比对之前

`auth.py:188-190`：只要 `API_KEY` 与 `JWT_ENABLED` 都为空就直接 `return {"type":"dev"}`。
此时**带一个乱写的 `X-API-Key` 也返回 200**（`auth.py:193` 的比对根本没走到）。

当前 `.env` 恰好配了 `JWT_SECRET` 所以没触发 ——
但**默认值就是"什么都没配"**，任何新克隆 / 新环境都会裸奔。
另外 `auth.py:105` 的注释宣称 `jti` 防重放，而 `decode_jwt:133` 只验签名与过期、
jti 从不落库校验 → **无重放防护**，注释与实现不符。

#### F42【中】CORS 实际比注释更宽

`middleware.py:246-253` 用 `allow_origins=["*"] + allow_credentials=True`。
实测把 `Access-Control-Allow-Origin` **回显为任意 Origin**（如 `https://evil.example`）
且带 `Allow-Credentials: true`，预检也放行 `x-api-key`
→ 任意网站可以从访问者浏览器驱动这个 API（当前无 cookie，实际危害 = 跨站盗刷 LLM 额度）。

#### F43【中】`kb.html` 是存储型 XSS 面（与 F38 叠加后攻击面完整）

`chat.html` 全程 `escapeHtml`，但 `kb.html` 只在题库卡片转义：
`${d.source}`(360)、`deleteDoc('${d.source}')`(365)、`${r.text}`(428)、
`${dir.name}`(543)、`${file.name}`(552) 直接进 `innerHTML` / 内联 `onclick`
→ 知识库内容或文件名里的 HTML/引号即可执行脚本，或让"删除"按钮直接失效。

再叠加 F38 的任意文件入库 —— 攻击者可以把恶意内容写进知识库，再等人打开管理页。
另外 API Key 存在 `localStorage`（`chat.html:181`），配合 XSS 可被直接读走。

#### F44【中】全局异常处理器把内部细节回吐客户端

`middleware.py:204-210` 用 `detail=str(exc)[:100]`。
实测响应体直接带出磁盘路径，甚至一个 `api_key=sk-...`。

（顺带澄清一个疑问：它**不会**吃掉 SSE 流 —— 流已开始后它只能写日志，
客户端看到的是断流。真正的问题是 F34 的协议不闭合。）

#### F45【架构级】`config` 是导入期硬依赖 → 全项目无法在无凭据环境导入

`config.py` 在模块顶层执行 `ZHIPU_API_KEY = _require("ZHIPU_API_KEY")`，缺失即抛。实测（清空环境变量）：

**建议方向**：惰性校验（真正调 API 时才校验）或 `pydantic-settings` 显式构造。

#### F46【中】命名与职责混淆：`question_bank.py`（构建器）vs `qbank.py`（读取器）

| 文件 | 行数 | 职责 | 类型 |
|------|------|------|------|
| `course_agent/question_bank.py` | 1163 | 从 PDF **构建**题库 JSON + 切题图（调 VLM/LLM） | CLI 入口点 |
| `course_agent/qbank.py` | 895 | **读取**题库：分组、编号、解析、批改依据 | 库 |

同目录、同前缀、同领域词，导入名只差两个字符，职责相反。
后果已经发生：`qbank.py` 的 docstring 与 5 处注释都在描述"构建脚本产出的脏数据"
（`display_num` 跨题型共用、`q_num=4.1`、填空题 answer 是单选字母）——
**读取层被迫长期替构建层补契约**。

**建议方向**：改名 `scripts/build_question_bank.py`，两边模块头互写"禁止互相 import"。

#### F47【中·已复核】`/health` 不在限流豁免表 → 探活会被判死

`middleware.py:58` 与 `:166` 的豁免表是 `["/", "/favicon.ico", "/docs", "/openapi.json"]`，
而真实健康检查端点是 `/health`（`server.py:87`）。
**我独立复核：把上限设为 2，连续 4 次 `/health` → `[200, 200, 429, 429]`。**

更值得说的是它为什么没被测出来：`tests/test_middleware.py:117` 断言的是 `/` 不限流
—— **测试测了一个无意义的豁免项，掩盖了真实端点的问题**。

#### F48【中】限流粒度=纯 IP，不看 `X-Forwarded-For`

`middleware.py:162` 只用 `request.client.host`。直连时这样是对的（不可伪造），
但一旦跑在 nginx 后面就退化成**全世界共用一个桶**，一个人能打满全站；
反过来无脑信任 XFF 又会被人伪造绕过。
正确做法是显式配置可信代理层数、取右侧第 N 跳，计数放 Redis，维度用 `user/key + IP`。
另外 `RATE_LIMIT_PER_MINUTE` 默认 0（`config.py:91`）= 默认关闭。

#### F49【中】请求日志对 SSE 记的是"首字节耗时"

`middleware.py:73-86` 的 duration 在 `call_next` 返回时就算完了。
一条流式路由会显示 `200 | 0ms`，而流还在继续 —— **300 秒的 LLM 流被记成几毫秒，P99 完全失真**。

#### F50【中】未捕获异常的日志丢 trace_id，两边对不上

`middleware.py:92-94` 在 `finally` 里先 `clear_trace_id()`，全局处理器随后才记录。
实测日志没有 `[trace]` 前缀，而客户端拿到的 `X-Trace-Id` 是另一个值 → 无法用追踪号反查日志。

#### F51【中】所有模块共用 logger 名 `"agent"`，且默认不落盘

`logger.py:92` 所有模块都 `logging.getLogger("agent")`，
而 `ColorFormatter:61` 打印 `record.name` → **每条日志的模块名恒为 `agent`**，
出问题无法从日志定位文件。
`LOG_FILE` 默认空且 `.env` 未设 → **默认零持久化日志**；
`server.py:309/449` 的 `traceback.print_exc()` 走 stderr，即使配了 `LOG_FILE` 也进不了文件。

#### F52【中】错误信封三套并存

| 形态 | 出处 |
|---|---|
| `{code, msg}` + **HTTP 200** | `server.py:531` 导入失败、`:556` 删除不存在的文档 |
| `{code, msg}` + HTTP 4xx/5xx | `middleware.py:204/216/227` |

F40 就是这个混乱的直接受害者：前端只判 `res.ok`，于是显示成"HTTP 401"。

#### F53【中】`errors.py` 的异常体系一半是死的

`APIError` / `RateLimitError` / `ToolError` 全项目**从未被 raise**
（只有 `EmbeddingError` 与 `LLMError` 在用）→ `retry_on_rate_limit` 的

模块 docstring 第 11-12 行承诺"429 最多 3 次、超时固定 2 次"，实现里两个分支共用 `max_retries=3`。
`safe_tool_invoke`（:116-135）把异常吞成字符串返回 → Agent 无法区分"工具失败"与真实内容。

#### F54【中】`chat.html` 前端结构：726 行内联 JS、全局状态、片段复制

#### F55【中】手写 Markdown 渲染器在**常见输入**上就产出错误 HTML

`chat.html:698-715` 先 `escapeHtml` 再依次替换，**段落切分放在最后**。实测：

## 四、面试问答准备

### 4.1 架构类

**Q：为什么有两套 Agent 实现？**
A：模式 A（LangGraph）是路线要求，覆盖 Plan-and-Execute 与 ReAct；模式 B（手写循环）
是我作为用户想要的学习/复习 Agent，用来自验证"LLM 主导会不会比状态机灵活"。
手写让我能控制每一步（流式 tool_call 拼装、会话 TTL、上下文压缩），
但代价是约 28% 的代码在重写框架白送的能力。这条线的完整复盘在
[完整生命周期](案例-手写助教的完整生命周期.md)。

**Q：如果要上生产，你最先改什么？**
A：三件事，按顺序：
① 会话持久化 —— 现在两份状态都在进程内存（`MemorySaver` + `_SESSIONS`），
重启即丢、多 worker 不共享，应换 `SqliteSaver`/`PostgresSaver`；
② 修 checkpointer 串味 —— 两个图共用一个 `MemorySaver` 且前端切模式不换 thread_id，
已复现跨模式读到对方状态；
③ 补 Agent 决策日志 —— 现在 nodes/tutor 两个编排层各只有 1 次 logger 调用，
线上出问题查不到"为什么这么决策"。

**Q：依赖结构有什么问题？**
A：`rag_tool` 与 `knowledge_pipeline.pipeline` 循环依赖（被函数内延迟导入掩盖），
且 `rag_tool` 反向依赖 `course_agent.errors/logger`。
根因是 `errors`/`logger` 没被下沉为独立基础设施层。

### 4.2 数据链路类

**Q：你的知识库有多大？怎么组织的？**
A：4199 个分块，课本 2319（55%）、PPT 1827（43.5%）、笔记 53。
但要如实说一个短板：**"按章节组织"目前是假的** ——
`chapter` 元数据与来源文件是 1:1（20 个来源里 0 个有多个 chapter 值），
课本那 55% 的 `chapter` 是空的。原因是 pipeline 抽出的页/章结构在入库时被 join 抹平了
（`pipeline.py:60` 与 `:72`），而 meta 里没有 page/section 字段。

**Q：`use_pipeline=True` 改变了什么？**
A：只改变"文本怎么来"，不改变"文本怎么进库"。分叉点只在 loader
（`rag_tool.py:585-595`）：经典路是 pypdf 原文 + `clean_text`；流水线路是 PPT 逐页 + VLM 描述、
课本 LLM 笔记。之后两路汇合到同一个 `chunk_text` + embedding + upsert + 同一套 meta。
实测 3 页幻灯片合并后不到 300 字 → 只切出 1 个块。

**Q：批量调 LLM 出错怎么办？**
A：有重试（3 次 + 429 退避），但**没有终态**：失败返回 `{}`/`""`，
调用方只标 `needs_review=True`，不抛异常、不改退出码，"完成"照打。
也没有断点续跑 —— 图片在调 LLM 前就全部落盘，JSON 最后才写，
中途挂掉就是"一堆孤儿图片 + 没有 JSON"，重跑重付全部费用。

**Q：题库两次构建/读取的契约是什么？**
A：老实说：**没有强制契约**，靠"两边记得同一批字段名"。
而且现在读到正确的 191 题，是**加载顺序的巧合** ——
单卷 JSON（191 题）先加载、合并文件（125 题）后加载，`setdefault` 先到先得。
一旦顺序或去重策略变了，会静默丢 66 题。这正是我后来发现的坑。

### 4.3 工程化类

**Q：怎么保证质量？**
A：278 项测试（`pytest tests/`），覆盖题库解析、批改、检索阈值、记忆压缩、
鉴权、中间件、图片处理。**但要说清边界**：没有 CI（全靠手动跑）、

**Q：线上一次回答错了，你怎么查？**
A：目前**查不深**。请求级有 trace_id（`ColorFormatter` 从 contextvars 自动注入，

但 `nodes.py` 457 行只有 1 次日志、`tutor_agent.py` 1251 行只有 1 次 ——

这是我下一步最想补的（成本很低、收益很大）。

### 4.4 安全与鉴权类（**必须准备好，这是最容易被问穿的一节**）

**Q：你的鉴权是怎么设计的？为什么有的接口有、有的没有？**

诚实答：`Depends(any_auth)` 是**逐个路由手写**的。
`/qa/ask` 在第 9 周加了，而第 6 周写的 `/qa/stream` 忘了加 ——
偏偏前端实际调的就是 `/qa/stream`（`chat.html:534`）。
所以"加了鉴权"这件事，**挡住的恰好是没人用的接口**。
我逐路由复核过：需鉴权的只有 `/qa/ask`、`/kb/add`、`/kb/add-directory`、
`DELETE /kb/documents/{source}`；而 `/qa/stream`、`/tutor/stream`、`/kb/search`、
`/kb/documents`、`/kb/browse`、`/qb/*` 全部匿名可用。

正确做法：依赖挂到业务 `APIRouter` 上**默认拒绝**，只显式放开 `/health`、`/chat`、`/kb`、`/docs`。

**Q：路径穿越怎么防的？**

只有 `/kb/browse` 做对了（`resolve()` + `relative_to`，实测 `../../course_agent` → 403）；
`/kb/add` 和 `/kb/add-directory` **完全没有包含性校验**：`file_path` 直接进 `add_document` →
只做 `Path(file_path).exists()` → `_classify_doc` 在路径不在 `data/` 下时
**退回按全路径判断并默认返回 `notes`** → 任意 md/txt/pdf/docx 都被当笔记入库。
再配上无鉴权的 `/kb/search`（返回 chunk 全文）就是一条**任意文件读取链**。

而这条链的入口更宽松：`/auth/login` **不校验密码**（`password` 字段从未被读取，
实测任意用户名 + 任意密码 → 200 返回 token）。所以它不需要"先有凭证"。

修法：一个 `resolve_within(base, p)` 工具函数、`data/` 可配置、扩展名/大小白名单、
该加鉴权的都加、登录真校验。

**Q：限流为什么按 IP？**

按 IP 只在"客户端直连"时成立且不可伪造（这点是对的）；
但代码只看 `request.client.host`，**完全不看 `X-Forwarded-For`**，
所以一挂到 nginx 后面就退化成**全世界共用一个桶**，一个人能打满全站。
反过来无脑信任 XFF 又会被伪造绕过 —— 正解是显式配置可信代理层数、取右侧第 N 跳，
计数放 Redis，维度用 `user/key + IP`。

顺带承认一个我自己踩的坑：`/health` 漏在限流豁免表外（豁免表里放的是毫无意义的 `/`），
而我的测试恰好断言的是 `/` —— **测试绿了，真实探活端点会被 429 判死**。
这是"测试测了错误的对象"的典型例子。

**Q：CORS 配 `allow_origins=["*"]` 有什么问题？**

配合 `allow_credentials=True`，实测会把 `Access-Control-Allow-Origin`
**回显为任意 Origin** 并带 `Allow-Credentials: true`。
当前没有 cookie，所以实际危害被限制在"跨站盗刷 LLM 额度"，但这是不该留的默认值。
