# 方法论：Agent 灵活性流失 —— 成因、检查表与瘦身

> **本文由两篇旧文档合并而成**：
> `Agent灵活性流失-成因与检查表.md`（诊断：为什么会照本宣科，原 297 行）
> + `Agent脚手架瘦身方案.md`（对策：怎么把固定开销降下来，原 356 行）。
> 合并原因：它们是同一个问题的「为什么」和「怎么办」，分开看会缺一半。
>
> **一句话结论**：同一个 GLM，裸用很灵活，套上 Agent 反而照本宣科 ——
> **不是模型变笨，是我们在它和用户之间插了三层东西。**
>
> 用途：技术笔记 / 后续 Agent 设计的自查清单。
> 全部证据可在代码与 `debug/` 脚本中复现。

---

## 一、现象（用户原话）

| 场景 | 表现 | 期望 |
|---|---|---|
| 说「我不会」 | 回「请仔细阅读题目……祝你好运」，或只丢答案不给解析 | 讲清这题怎么做 |
| 答 `AAAAA` | 「看起来您没有提交答案，请完成题目后再次发送」 | 识别为「全选 A」并批改 |
| 答 `E`（四选项题的乱答） | 「没识别出来」 | 正常判错 |
| 说「继续刷题」 | （游标）到了下一组，但**一条题都没给** | 出下一组题 |
| 说「另外出几道题」 | 拿计网题冒充「死锁专题」 | 真的出死锁题 |

用户的直觉质疑（本文要回答的）：

> 「我们用的 GLM 本人是可以判题的，也可以识别我乱给的答案，也可以在我提出其他要求的时候
> 去做别的、不会死磕一定要我给出这题答案才放我走 —— **为什么做成 Agent 它反而照本宣科了？**」

---

## 二、摘要（可直接引用）

> 排查 Agent「照本宣科」的问题时，我最后定位到的不是模型能力，而是 Agent 脚手架本身。
> 它引入了三个独立的失真源：
> **① 信息不完备**（我们替模型决定什么进上下文，裁掉了它做判断所需的信息）；
> **② 契约冲突**（工具 schema/描述成了比 prompt 更硬的规章，和用户意图打架）；
> **③ 状态不可见**（系统状态存在代码变量里，模型只能间接感知，变化时它不知道）。
>
> 有效的修复都不是「再加一条规则」，而是**补信息、减职责、让状态可见**。
> 反过来，规则堆得越多，模型越只在规则内活动 —— 这就是「照本宣科」的生成机制。

## 三、机制一：信息不完备 —— 我们替模型裁掉了它做判断所需的东西

### 3.1 现象

用户说「我不会」，模型的原话是：

> 这是一道关于网络性能的选择题，**具体题干和选项我无法提供**。
> 请您仔细阅读题目，根据自己的理解选择最合适的答案。……
> 希望这些信息能对您有所帮助。祝您好运！

### 3.2 根因

出题工具为了「防泄题」，**只返回题号/题型/知识点/图片 URL**，`text`（题干）
和 `answer`（答案）根本不进模型上下文。于是：

- 学生做题阶段：很好，模型没有答案可泄；
- 学生卡住要讲解时：**模型手上没有题目，物理上讲不了题**。

它只能填一些通用知识（「网络性能包括传输速率、带宽、延迟、吞吐量……」）
加上空泛鼓励，因为它没有别的合法素材。

**为什么裸 GLM 不会这样**：裸用的时候题目是你贴进对话的 —— **上下文是完备的**。
Agent 化之后，「什么该进上下文」的决定权从「对话自然携带」变成了「由代码裁剪」，
而代码是按某个目标（防泄题）裁的，顺手把另一个目标（能讲题）所需的材料也裁掉了。

### 3.3 顺带发现的双重打击

旧 SYSTEM_PROMPT 里还明确写着：

```
❌ 绝对不能自己判断对错，你的判断不可靠
❌ 绝对不能编造答案
```

**既没给题面，又禁止推理** —— 模型剩下的唯一合法动作就是「说空话、让你再试试」。
这条规则本身有正当理由（LLM 判题不可靠、会编答案），但它和「裁掉题面」叠加后，
把模型逼到了唯一一种僵硬行为上。

### 3.4 教训

> **防泄题 ≠ 不给模型题面。** 正确做法是「按需取用」：
> 出题时不给，真要讲解时用一个专门工具取回来（本项目落地为 `explain_question`）。

## 四、机制二：契约冲突 —— 工具描述成了比 prompt 更硬的「规章」

### 4.1 现象

`grade_answers` 的工具描述里，本意是举例说明支持的格式：

> 支持多种答案格式：`1.A 2.B`、`ABCDA`、`1.对 2.错` 等，工具会自动解析。

用户的输入是 `AAAAA`，模型判定「不在允许清单里」，于是拒绝：

> 看起来您没有提交答案，请完成题目后再次发送答案。

### 4.2 根因

**模型对工具 schema / description 的服从度，高于对自然语言 prompt 的服从度。**
因为工具描述在 API 层面是「能力契约」，模型倾向于把它当成**枚举规范**来遵守：
「既然只列了这三种，那别的不合法」。**举例本意是想放宽，实际效果是收窄。**

### 4.3 一个更隐蔽的版本

`_wants_custom_quiz()` 这类意图守卫，以及旧版的 `_is_quiz_answer(text)`，
本质都是「用代码硬判用户想干什么」。一旦用户的说法不在预期内，就被分流到错误分支 ——
用户抱怨的「死磕」就是这么来的：

```
review.py（已删除的状态机版）：
    _is_quiz_answer(text)   ← 硬编码意图判断
    不在预期说法内 → 被当成别的东西处理
```

有意思的是，重构后长出来的 `_wants_custom_quiz()` 是**同一个问题的弱化版**。
两者不是「死板 vs 灵活」，而是**同一条光谱上的两个点**。

### 4.4 教训

> **schema 说「是什么」，返回值说「怎么用」。**
> 需要放宽的地方，不要写成枚举清单，而要写成「边界 + 兜底承诺」：
> 「只要像作答就原样传进来，格式由工具解析；解析不了工具会如实告诉你。」
>
> 并且**尽量别让代码去猜用户意图**：能靠工具返回值兜住的，就不要用正则判意图。

## 五、机制三：状态不可见 —— 状态在代码里，模型看不见自己的处境

### 5.1 现象

用户做完一组题说「继续刷题」，**游标前进到了下一组，但一条题都没给**；
之后说「我没看到题目」，模型回：

> 很抱歉，可能是由于格式问题导致题目没有正确显示。请稍等，我将重新发送这组题目。

—— 然后**没有调用任何工具**，一条题也没发。

### 5.2 根因

刷题进度存在会话字典里（`session["last_group"]`、`session["current_qids"]`），
**不在对话里**。于是出现两个断裂：

1. 工具调用**推进了游标**（代码里发生了状态变化），但没有任何**可见事件**
   告诉模型「学生其实没看到这一组」；
2. 模型「以为自己发了」（它取到了数据），「其实没发」（回复里没贴题）。

裸 GLM 没有游标 —— 它的「进度」就在对话历史里，看得见、改得动。

### 5.3 教训

> **凡是代码里发生的状态变化，都要在模型可见的地方留下痕迹**；
> 能放进对话的，别只放在变量里。
> 更进一步：**输出即状态** —— 给出「可以直接发出去的成品文本」（本项目落地为
> `reply_text`），比给出「数据 + 展示建议」可靠得多，因为前者不会出现「取到了但没发」。

## 六、量化：注意力配比

测量脚本：`debug/quantify_scaffolding.py`

```
LLM 助教一轮对话，模型上下文里各部分的体积（8 工具时代）
  SYSTEM_PROMPT（人设 + 工作习惯）      488 字符  ≈  244 tokens
  工具定义（8 个工具的 schema）        3667 字符  ≈ 1833 tokens
  ─────────────────────────────────────────────────────
  固定开销合计                        4155 字符  ≈ 2077 tokens

  用户这句话「我不会」= 3 字符 = 固定开销的 0.07%
  用户这句话「AAAAA」 = 5 字符 = 固定开销的 0.12%
```

**模型要读完 4155 字符的规程，才轮到读你那 3 个字。**
它是在「我该调哪个工具、契约要求我怎么做」的框架里思考，
而不是在「这个学生卡住了」的框架里思考。

补充数据（知识寻回BOT / LangGraph 模式）：

```
PLANNER_PROMPT        1235 字符
SYNTHESIZER_PROMPT     494 字符
REACT_PROMPT           738 字符
CHITCHAT_PROMPT         94 字符   ← 闲聊的 prompt 最短，很说明问题
```

而且该模式是**先**把用户的话转成 JSON 计划再执行 ——
用户原话在 planner 那一步就被压缩成 `{"steps": [...]}` 了。

## 七、⭐ 检查表（核心产出）

设计或排查一个 Agent 时，问这三个问题：

| # | 维度 | 问什么 | 失守时的症状 |
|---|---|---|---|
| 1 | **信息完备性** | 模型此刻做这个判断，所需的信息在它上下文里吗？ | 说空话、答非所问、「我无法提供…」 |
| 2 | **契约冲突** | 有没有硬性接口约定在和用户意图打架？ | 拒绝合法输入、「请按格式重发」 |
| 3 | **状态可见性** | 系统的状态变化，模型能感知到吗？ | 行为与实际状态错位（以为发了、其实没发） |

本次 5 个用户反馈**恰好一一落在这三格里**：

| 反馈 | 落在哪一格 |
|---|---|
| 「我不会」讲不了题 | 信息完备性（缺题面） |
| `AAAAA` 被拒 | 契约冲突（枚举清单被当规章） |
| `E` 认不出 | 信息完备性/解析层（选项范围写死 A–D） |
| 「继续刷题」没给题 | 状态可见性（游标推进无可见事件） |
| 「另出题」张冠李戴 | 契约冲突（工具范围 vs 用户意图） |

### 7.1 修复方向对照表（本项目实例）

真正让用户觉得「终于对了」的修复，**没有一个是「再加一条规则」**：

| 方向 | 本项目落地 | 效果 |
|---|---|---|
| **补回被裁掉的上下文** | `explain_question`：按需取回题面 + 参考答案 + 参考要点 | 从「无法提供题干」→ 能按考点→推导→错项分析→记忆点一步步讲 |
| **减少模型的职责** | `reply_text` / `_render_example` 直接给成品文本；明确「格式判断交给工具，你只管原样转发」 | 转录漏段消失；`AAAAA` 被正常批改 |
| **让状态变化可见** | 重发守卫（说没看到题就重发当前组、不推进游标）+ 主循环里一次确定性纠偏 | 「只道歉不发题」被兜住 |
| **把枚举改成边界** | 题号标记支持中文数字/连写；「整组同一选项」；字母范围 A–H | 一大批自然写法都能识别 |

## 八、反面教材：看起来能修、其实在加约束

| 做法 | 为什么是错的 |
|---|---|
| 在 prompt 里加更长的「铁则清单」（旧版 57 行） | 规则越多，模型越只在规则内活动；且它会念规则、显得机械 |
| 用正则判用户意图（`_is_quiz_answer`） | 用户说法稍有变化就分流错；这是「死磕」的直接来源 |
| 为了省 token 按阶段动态加载工具子集 | **直接违反信息完备性**：需要某工具时它看不见。本次所有修复都是反方向（把工具显性化） |
| 解析不出来就「兜底塞给第 1 题」 | 等于凭空造一个批改结果；正确做法是如实返回空 + 说明 |
| 出错就返回 `False` / `None` | 语义上是「放弃判断」，学生会看到「需人工核对」而不是得到帮助 |
| **削减 SYSTEM_PROMPT** | 它承载「学生说不会要真的教」这类防退化说明，风险大于收益 |
| **把 `reply_text` 挪回 schema 当「格式要求」** | `reply_text` 的价值恰恰在于它是**数据**（成品文本）而不是**要求** |

## 九、瘦身：把固定开销降下来

### 9.1 现状测量（哪些地方最贵）

`debug/measure_schema.py` 实测，按 schema 体积排序（8 工具时代）：

| 工具 | schema 合计 | 其中描述 | 其中参数 | 参数个数 |
|---|---|---|---|---|
| `grade_answers` | 714 | 262 | 352 | 3 |
| `get_paper_questions` | 641 | 236 | 304 | 3 |
| `prepare_custom_quiz` | 631 | 142 | 387 | 5 |
| `explain_question` | 502 | 102 | 301 | 3 |
| `search_knowledge_base` | 456 | 38 | 316 | 4 |
| `list_papers` | 268 | 49 | 127 | 1 |
| `record_practice` | 228 | 32 | **100** | 1 |
| `get_practice_stats` | 211 | 12 | **100** | 1 |
| **合计** | **3651** | 873 | 1987 | |

**两个关键观察**：

1. **参数 schema 比描述更贵（1987 vs 873）** —— JSON 参数条目的固定成本很高
   （每个参数至少 `"type"` + `"description"` 两个键，约 100 字符）。
   所以**砍参数比砍描述更划算**。
2. **两个练习统计工具合计 439 字符，而这个功能从未被用过。**
   证据：`practice_stats.json` **不存在**（调用过就会写出来）；前端没有展示；
   全局搜索只出现在定义/文档/测试里，**没有消费方**。

### 9.2 优化项（按「收益 / 风险」排序）

**L1. 把「呈现契约」从 schema 搬到返回值 —— 双赢，优先做**

原理：schema 说「是什么」，返回值说「怎么用」。现在两边重复，而 schema 那一份会变成规章。

| 工具 | 现在描述里有什么 | 应该只留什么 |
|---|---|---|
| `grade_answers` | 格式枚举清单（262 字符）→ **正是它导致 AAAAA 被拒** | 「像作答就原样传，格式由工具解析；解析不了会告诉你」（约 80） |
| `get_paper_questions` | 分组规则 + 展示要求（236） | 「取一组题」（约 60）；细节都在返回值的 `reply_text` / `_guide` 里 |
| `prepare_custom_quiz` | 适用场景说明（142） | 「取临时出题的素材」（约 70） |
| `explain_question` | 调用时机说明（102） | 「取题面与参考答案用于讲题」（约 60） |

> 注意这不是「删信息」—— 这些信息会以 `_guide` 形式出现在工具**返回值**里，
> 时机更准（就在该用的时候出现），也不会被当成全局规章。

**L2. 合并/剔除练习统计工具 —— 省 439 字符 + 2 个决策点**

| 方案 | schema 变化 | 说明 |
|---|---|---|
| (a) 合并成 `practice_stats(action="get"｜"record")` | 439 → 约 230 | 保留能力，参数化 |
| (b) **直接删掉两个工具** | 439 → 0 | **推荐**：功能从未被调用、没有 UI、没有消费方 |
| (c) 保持现状 | 0 | 保留「以后可能要做」的想象 |

推荐 (b)，理由：**没有需求驱动的能力就是负债** —— 它既占 schema、又占模型的决策面。
实现代码只有 23 行，将来真要做，加回来成本极低。

**L3. 压缩 `prepare_custom_quiz` 的参数（5 → 2）**

现在 5 个参数（`topic`/`course`/`qtype`/`count`/`difficulty`），参数 schema 387 字符。
改成 `topic`（必填）+ `request`（自由文本，如「5 道选择题，进阶难度」）→ 约 150。
理由：出题本来就是模型自己写，那 4 个参数只是提示，自由文本一样能表达**且更灵活**
（「来 3 道送分题」这种结构化参数反而表达不了）。

**L4. `explain_question` 去掉 `qids` 参数（保留实现支持）** —— schema 只留 `no`，
实现里继续支持 `qids`（向后兼容、方便手写调用），只是不告诉模型。省约 100 字符。

**L5. `search_knowledge_base` 去掉 `chapter` 和 `top_k`** ——
`top_k` 默认 5 就够、由代码固定；`chapter` 有了按课程的 `sources` 过滤后基本冗余。省约 166 字符。

**汇总预期**：L1~L5 合计省 ~1545 字符、工具数 8 → 6；
固定开销 4155 → 约 2610 字符（**-37%**）；`SYSTEM_PROMPT` **不动**。

### 9.3 明确**不做**的方案（以及为什么）

这一节和方案本身同样重要 —— 有些「看起来能瘦身」的做法方向是错的。

| 方案 | 为什么不做 |
|---|---|
| **按会话阶段动态加载工具子集** | **直接违反信息完备性**。学生可能在任何时刻说「另外出几道题」，此时模型若看不到 `prepare_custom_quiz` 就只能拒绝或瞎编。这是最诱人也最危险的一条 |
| **削减 SYSTEM_PROMPT** | 它承载防退化说明，风险大于收益 |
| **用规则/正则替代工具** | 这就是契约冲突那条机制的根源，用户说法千变万化，正则一定误判 |
| **把 `reply_text` 挪回 schema** | 会从「数据」退化成「规章」 |
| **合并 `list_papers` 与 `get_paper_questions`** | 省约 150 字符，但牺牲「描述即说明用途」的清晰度 —— 收益边际，**倾向不做** |

### 9.4 执行计划（分阶段，每阶段独立可验证）

**阶段 0：建立行为基线（必须先做）** —— 瘦身最大的风险是「悄悄退化」：

```bash
.venv/Scripts/python.exe -m pytest tests/ -q                    # 单元测试基线
.venv/Scripts/python.exe debug/e2e_quiz_flow.py                 # 刷题→出题→批改→换要求
.venv/Scripts/python.exe debug/e2e_custom_quiz.py               # 「另外出几道题」
.venv/Scripts/python.exe debug/verify_complaints.py             # 「我不会」+ AAAAA
.venv/Scripts/python.exe debug/verify_e_and_recovery.py         # E + 没看到题目
```

**判定基线**（9 条断言，改前必须全绿）：

| # | 断言 | 对应检查表维度 |
|---|---|---|
| 1 | 「我想刷题」→ 两门课所有卷子都列出，且提到可另出题 | 信息完备性 |
| 2 | 选卷 → 5 题一组，每题带题号+知识点+图片 | — |
| 3 | 提交答案 → 批改，且错题给出解析（不只报答案） | 信息完备性 |
| 4 | 「我不会」→ 调 `explain_question`，有推导，无空泛鼓励 | 信息完备性 |
| 5 | `AAAAA` / `全都选A` / `AAAAE` → 被批改，不出现「没提交答案」 | 契约冲突 |
| 6 | 四选项题答 `E` → `correct=False` 且给出正确答案（不是「需人工核对」） | 解析层 |
| 7 | 「继续刷题」→ 真的给出题目 | 状态可见性 |
| 8 | 「我没看到题目」→ 重发同一组（不推进、不空口承诺） | 状态可见性 |
| 9 | 「另外出几道题」→ 走 `prepare_custom_quiz`，不拿题库题冒充 | 契约冲突 |

**阶段 1：低风险双赢** —— L1 描述搬家 + L4 去 `qids` + L5 去 `chapter`/`top_k`。
预期省约 866 字符，**且同时降低「枚举当规章」的风险**；不删任何能力，只改「信息放在哪一层」。

**阶段 2：中风险（需产品决策）** —— L2 删练习统计工具 + L3 压缩参数，
预期再省约 680 字符、工具数 8 → 6。

### 9.5 验证方法（怎么证明「更灵活」而不是「更糟」）

| 指标 | 怎么测 | 期望方向 |
|---|---|---|
| 固定开销字符数 | `debug/measure_schema.py` | 下降 |
| 「拒绝 / 空话」出现次数 | 统计 e2e 输出里 `没认出｜无法提供｜没有提交｜格式不对｜祝你好运` | 保持 **0** |
| 工具调用次数 | e2e 输出里的 `工具: [...]` 长度 | **不追求下降**：省一次调用不代表更好，该调的还得调 |

> **关键原则**：瘦身不是目标，**「在更少规矩下保持同样可靠」才是目标**。
> 某个阶段的行为断言出现任何一条变红，就回退该阶段，不做「调参补回来」。

## 十、⭐⭐ 踩到的两个坑（比技术结论更值得记）

### 10.1 坑一：L1 的假设只对了一半

L1 的原假设是「描述里的枚举会被当成规章，所以要把枚举删掉」。
**删掉之后行为反而退化了**：

```
学生发「1.D 2.B 3.D 4.A 5.C」（完全规范的作答）→ 模型不调 grade_answers，反而要求：
  「请按照以下格式提交答案：题号. 知识点 + 答案」
```

它把**出题列表的展示格式**（题号 + 知识点 + 图片）当成了**作答格式**。

原因：删掉枚举之后，模型手里只剩一个格式信号（题目怎么展示的），
而**没有任何关于「学生答案长什么样」的信号**，那个真空就被展示格式填上了。

所以正确做法不是「删枚举」，而是**把枚举改写成「举例而非穷尽」**：

```
学生发来的内容只要像作答就原文照传，例如「1.A 2.B」「ABCDA」「AAAAA」
「全都选A」「第一题C」「对错对错」—— **这是举例，不是穷尽**，凡是作答写法都交给工具去解析。
```

同时把「答案怎么写都行」写进 `reply_text`（发给学生的那段话）——
这样既给了模型关于作答格式的明确信号，也直接告诉学生**不用照展示格式提交**。

> **教训**：schema 里的举例要显式标注「举例而非穷尽」。
> **删掉例子不等于放宽** —— 没有例子时模型会自己发明规矩，往往比原来的例子更严。

### 10.2 坑二：差点把「测试脚本的 bug」当成「代码回归」

上面那个「模型要求按 题号+知识点 提交答案」的现象，我一度判定为 L1 造成的回归。
**它是我的探针脚本自己的 bug。**

```python
CASES = [("规范题号", "1.D 2.B 3.D 4.A 5.C"), ...]   # (标签, 作答文本)

for text, label in CASES:        # ← 变量接反了！
    ... process_message(sess, text)   # 发出去的是「规范题号」这四个字
```

于是脚本实际发给模型的是「规范题号」—— 模型一本正经地解释
「规范题号的格式是：题号 + 知识点」，看起来**完全像**「模型在刁难学生格式」。

而同一时期另一个写对了的 A/B 脚本（`ab_grade_description.py`）三个变体都是
转发 3/3 —— **那个正确的信号被我忽略了**，因为我更相信自己刚「读到」的现象。

修正变量顺序后重测（`debug/probe_answer_forwarding.py`）：
**12 次全部转发成功，0 次要求格式。**

**方法论教训（比技术结论更值得记）**：

1. **观察到的「模型退化」，先怀疑观测工具**。探针脚本、断言条件、会话构造
   都可能是错的那一方。本次如果没写第二个独立诊断去交叉验证，
   就会基于假信号去改代码（我确实已经改了）。
2. **两个独立探针结论冲突时，优先信「写得更简单、变量更少」的那个** ——
   本次正确的那份脚本恰好也是最简单的（只有 `set_desc` 一个变量）。
3. **给探针加「自证」字段**：把「我到底发出去了什么」打出来。
4. **别用被测对象自己的术语当测试输入**。用「规范题号」这种像元语言描述的字符串
   做输入，本身就会诱导模型讨论格式 —— 输入应该是真实学生会打的东西。

## 十二、可直接引用的措辞（备选）

**版本 A（现象切入）**

> 我遇到过一个反直觉的现象：同一个 GLM 模型，直接对话时很灵活，
> 但包成 Agent 之后变得照本宣科 —— 学生说「我不会」它只会说「请再仔细看看」，
> 学生乱答个 AAAAA 它说「你没提交答案」。
> 排查后发现问题不在模型，而在 Agent 自己引入的三层失真：
> 我按「防泄题」裁剪了上下文，结果它讲不了题；我把工具描述写成了枚举清单，
> 结果它把不认识的输入当非法输入拒绝；我把进度存进了代码变量，
> 结果它不知道学生其实没看到题。
> 后来我把这三条总结成检查表 —— 信息完备性、契约冲突、状态可见性 ——
> 之后的修复就都集中在「补信息、减职责、让状态可见」上，而不是继续堆规则。

**版本 B（方法论切入）**

> 做 Agent 时最容易犯的错，是把「模型能力不足」当成主要矛盾。
> 实际排查下来，多数「模型不行」的情形，是**我们把它放到了一个信息不全、
> 规矩过载、状态不可见的位置上**。
> 判断标准可以很具体：模型现在要做的这个判断，所需信息在它上下文里吗？
> 有没有硬性契约在和用户打架？系统状态变了它能看见吗？

**版本 C（一句话）**

> Agent 的僵硬不是模型变笨，是脚手架把「信息、裁量权和状态」这三样从模型手里拿走了。
