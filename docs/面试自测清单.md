## P0-3 我报的那 5 个 bug 的根因链（这是你最值钱的部分）

> **为什么值钱**：这些是你**自己用出来的**观察，你有第一手材料，
> 而且它们串起了整个项目的关键设计。别当成"修 bug"，要讲成"设计发现"。

### ① "我说不会，它只让我再试试" → 信息不完备

| 项 | 内容 |
|---|---|
| 现象 | 学生说"我不会"，BOT 回"请仔细阅读题目……祝你好运" |
| 根因 | 我为防泄题，把 `text`（题干）和 `answer` 从出题工具的返回值里删掉了。**模型手里没有题，物理上讲不了题** |
| 修法 | 新增 `explain_question`：真要讲解时才按需取题面 + 参考答案 + 参考要点。**不是往 prompt 里加规则** |
| 定位 | `tutor_agent.py:627`（handler）、`quiz_service.py:254`（共享实现）、`quiz_service.py:246`（讲解顺序要求） |

### ② "我答 AAAAA，它说我没提交答案" → 契约冲突

| 项 | 内容 |
|---|---|
| 现象 | 学生发 `AAAAA`，模型回"看起来您没有提交答案" |
| 根因 | 工具描述里我写了"支持 `1.A 2.B`、`ABCDA`、`1.对 2.错` 等格式" —— 本意是举例，**模型当成了许可清单**，不在清单里就判定非法 |
| 修法 | 改成"**这是举例，不是穷尽**，凡是作答写法都交给工具解析"；并把"格式判断交给工具、你只管原样转发"写进契约 |
| 定位 | `tools.py` 的 `grade_answers` docstring、`quiz_service.py:119`（`_select_scope`） |

### ③ "答 E 它没识别出来" → 解析层写死

| 项 | 内容 |
|---|---|
| 现象 | 四选项题学生答 E（乱答），BOT"没识别出来" |
| 根因 | 全项目选项字母范围写死 `A-D`。**最危险的不是认不出，而是静默错位**：`ABCDE` 里的 E 被丢掉，后面答案整体前移 |
| 修法 | 放宽到 A–H；同时加**形状校验**（`_POSITIONAL_OK`）挡住 `"the answer is B"` 这种英文句子。四选项答 E 现在**正常判错并给出正确答案** |
| 定位 | `qbank.py:428`（`_LETTERS`）、`qbank.py:434`（`_POSITIONAL_OK`）、`qbank.py:633`（`_ALL_SAME`） |

### ④ "说继续刷题，它没给题目" → 状态不可见

| 项 | 内容 |
|---|---|
| 现象 | 做完一组说"继续刷题"，游标到了下一组，但**一条题都没给** |
| 根因 | 两层：出题工具只给了"排版示例"，模型可能只回一句"好的这是下一组"就结束，**游标却已经前进了** → 那组被静默跳过 |
| 修法 | ① 直接给**成品文本** `reply_text`（"输出即状态"）；② 重发守卫：学生说"没看到题"就重发**当前这一组**不推进游标；③ 主循环加一次**确定性纠偏** |
| 定位 | `quiz_service.py:307`（`group_payload`）、`tutor_agent.py:399`（重发守卫）、`tutor_agent.py:394`（`_missed_questions`） |

### ⑤ "为什么套上 Agent 反而照本宣科？" → 三条机制（这是你的**亮点问题**）

> 这是全场最好的一道题，因为它是**质疑自己的实现**，不是报 bug。

| 机制 | 含义 | 你的证据 |
|---|---|---|
| **信息不完备** | 我们替模型决定什么进上下文，裁掉了它做判断所需的信息 | 出题工具为防泄题拿掉题面 → 模型只能说空话 |

**量化证据**（很有说服力）：`SYSTEM_PROMPT` 488 字符 + 工具 schema 3667 字符

> **这是全场最好的素材**，因为它同时展示：主动质疑自己的实现、设计对比实验、

### 讲法（2 分钟版）

> 我一直以为两条路径都能用，直到我把**同一句用户请求**分别打给它们：

| 场景 | Plan-and-Execute | ReAct |
|---|---|---|
| 我想刷计算机网络的选择题 | ❌ **编造题目**，还编出 `https://example.com/net1.jpg` 假图 | ✅ 真图 `/qb_images/...` |
| 继续下一组 | ⚠️ **时好时坏** | ✅ 稳定第 2 组 |
| 第1题我不会 | ❌ 不调 `explain_question`，泛泛谈知识点 | ✅ 调了，引用真实题干与答案 |
| 另外出几道题 | ❌ 工具**根本没注册** | ⚠️ 有工具 |
| 正文 | ❌ 漏出 `get_paper_questions {...}` JSON 原文 | ✅ 干净 |

### ⭐ 一句话结论（背下来）

> **在 Agent 系统里，"工具结果要不要留在上下文里"这个看似不起眼的设计选择，
> 决定了多轮会话能不能成立。**

- **ReAct** 把含 `ToolMessage` 的整段历史交给模型 → 上一轮的 `next_group_index`
  留在**带内** → 跨轮状态自然存活
- **Plan-and-Execute** 为了让 planner 专注，**主动把 ToolMessage 从历史里剔掉**、
  assistant 内容截到 200 字 → 跨轮状态**无处安放**
  （`AgentState` 只有 `{messages, plan, tool_rounds}`）
- 定位：`nodes.py` 的 `planner_node`（排除 ToolMessage）+ `state.py`

### 四个叠加根因

1. `PLANNER_PROMPT` 把 `get_paper_questions` 写成"获取**所有**题目"，实际一次只给一组，且没提 `group_index`
2. 工具集合三处不一致（注册 9 个 / prompt 列 8 个 / 白名单又漏 `explain_question`）
3. 这些工具只返回"数据"，没有"该怎么呈现"的指引 → 模型认为需求没被满足，**自己编题**
4. 图是**单向**的（planner→executor→synthesizer），synthesizer 没有工具、一轮规划不够时只能编

### 三层修法（从便宜到贵，这个层次感要讲出来）

1. **改 prompt**（几分钟）→ `explain_question` 会调了，**但伪造还在**（诚实说这一步只成功一半）
2. **把"呈现契约"搬进工具返回值** → `list_papers` 附带"本步只列清单，不要开始出题"、
   `get_paper_questions` 给出 ready-to-send 的 `reply_text` → **伪造修掉**
3. **给 `AgentState` 加会话游标**：executor 从工具结果抽取 → planner 显式读进 prompt
   → 连跑 3 轮 **3/3 稳定推进**

### ⭐ 我最想说的一个教训（这句最值钱）

> **间歇性错误比稳定错误更危险。**
> 修复前 Plan 模式"有时也能推进组号"——因为模型偶尔能从**自己上一轮发出去的文字**里
> 反推出"第 1/19 组"该取第 2 组。所以**跑一次测试会通过**。
> 我最后是连跑 3 轮才敢下结论。

### 还有一条工程经验

> "加工具忘了改 prompt"这类 bug 只能用**一致性断言**挡。工具注册在 `tools.py`、
> 描述写在 `nodes.py` 的 prompt 里、白名单又写在第三个地方 —— 加一个工具要改三处，必然漏。
> 所以我加了 13 项枚举式断言："注册的工具必须都出现在 prompt 里"、
> "prompt 声明的工具数必须等于实际注册数"、"白名单必须覆盖所有刷题工具"、
> "不能把 `get_paper_questions` 说成取整卷"。

# P1 —— 让你从"能讲"到"讲得好"

## P1-1 RAG 那条线（面试官必问）

### 检索：为什么要混合检索？

```
查询 → 向量检索（语义相似）  ┐
     → BM25 检索（关键词精确）├→ 融合归一化分数 → 排序 → 按课程过滤 → 返回
                             ┘
```
**要点**：纯向量对**专有名词/代码符号**不敏感（"CFS"、"RTT=20ms"），
BM25 补这一块。定位：`rag_tool.py:495`（`_hybrid_search`）、`rag_tool.py:455`（`_get_bm25`）

### ⭐ 最容易出彩的一问：L2 距离和相似度是一回事吗？

**不是。** 这是这个项目里最隐蔽的一个 bug：

- 向量库用的是 **L2 空间**，`chromadb` 返回的是**距离**（越小越像）
- 代码却把距离当相似度用，于是**域外查询（距离 > 1）会算出负分**
- 修法：按空间换算 —— L2 空间用 `1 - d²/2`（单位向量下等价于余弦）

**第二个陷阱**：混合检索的融合分是**按最大值归一化**的（排名第一恒 ≥ 0.6），
而阈值判断需要**绝对**相似度。原来两处 `score < 0.3` 的判断都是拿归一化分比绝对阈值，
**分支永远不成立**（死代码）。

**要点**：`score`（归一化融合分，只用于**排序**）与 `sim`（绝对余弦，用于**阈值判断**）
必须分开。定位：`rag_tool.py:173`（`distance_to_similarity`）、`rag_tool.py:166`（`_collection_space`）、
`rag_tool.py:644`（`search`）

### 阈值 0.55 是怎么定的？

抽样 12 条域内查询（最低余弦 **0.665**）vs 12 条域外查询（最高 **0.524**），0.55 把 24 条样本 100% 分开。
**注意**：这个值作用在**绝对**相似度上，不能作用在归一化分上。定位：`config.py:142`

### `hnsw:space` 为什么重要？

建集合时如果不显式指定空间，Chroma 默认 L2；而代码假设的是余弦语义 ——
**空间语义和代码假设不一致，距离到相似度的换算就是错的**。定位：`rag_tool.py:434`

### 分块

`chunk_size=300, overlap=50`。**已知短板**（主动说）：
流水线抽出的"页/章"结构在入库时被 `join` 抹平了
（`pipeline.py:60` 的 PPT 走 `slides_to_text(merge_pages=1)`，`pipeline.py:72` 把课本多章笔记 `join` 成一个字符串），
meta 里没有 `page/section`。实测 `chapter` 字段与来源文件是 **1:1**（20 个来源里 0 个有多个 chapter 值），
课本那 55% 的 `chapter` 直接是空 —— **所以"按章节检索"目前是假的**。
定位：`rag_tool.py:335`（`chunk_text`）、`rag_tool.py:351`（`_chunk_fixed`）

## P1-2 上下文管理（`memory.py`，306 行）

三层策略：
1. **滑动窗口**：保留最近 N 条（`MAX_MESSAGES=20`）
2. **LLM 摘要**：超过 `SUMMARY_THRESHOLD=30` 条时，把老对话压成摘要（带 `SUMMARY_MARK` 标记）
3. **摊还缓存**：`_RESUMMARY_STEP=10` —— 每新增 10 条才重新摘要一次，避免每轮都调一次摘要 LLM

**踩过的坑（很好的深挖点）**：摘要缓存最初 **key 用内容哈希** →
不相关的两段对话如果内容碰巧相同，会**共用同一份摘要**（串味）。
改成 **message id** 作 key；拿不到 id 就**不缓存**（宁可不缓存也不要错缓存）。

**定位**：`memory.py:162`（`compress_history`）、`memory.py:142`（`_history_key`）、
`memory.py:137`（`_SUMMARY_CACHE`）、`memory.py:136`（`_RESUMMARY_STEP`）

**追问**：为什么 planner 和 synthesizer 的历史口径要一致？
→ 因为 `compress_history` 的缓存按历史内容命中，两边口径不一致就会**一轮摘两次**。定位：`nodes.py:139` 注释

## P1-3 安全决策（能体现工程成熟度，而且你有论证）

### 核心论证：为什么"关掉鉴权"是安全的？

> **边界校验与鉴权解耦。**

真正危险的那条链是：`/kb/add` 任意文件入库 → 经 `/kb/search` 把内容读出去。
而挡住它的是**处理函数内部的路径校验** `resolve_within_data()`，**不是鉴权**。

# 白板题准备：手写 agent loop

> 第 9 周要求"手写 Agent"，所以这是**唯一可能让你现场写**的东西。
> 核心不是代码，是**下面四个必须说出口的设计点**。

```python
MAX_ROUNDS = 6                     # ← ① 业务级轮数上限（没有它会跑到几千次）

def run(user_input, session):
    session["messages"].append({"role": "user", "content": user_input})
    for round_idx in range(MAX_ROUNDS):
        # ② 轮数用尽就别再给工具，逼它出最终答案
        tools = TOOLS if round_idx < MAX_ROUNDS - 1 else None
        content, tool_calls = call_llm(session["messages"], tools=tools)

        if not tool_calls:                      # 没有工具调用 = 最终答案
            return content

        # ③ assistant 的 tool_calls 必须原样回填，才能和 tool 结果配对
        session["messages"].append({
            "role": "assistant", "content": content, "tool_calls": tool_calls,
        })
        for tc in tool_calls:
            result = dispatch(tc["name"], json.loads(tc["arguments"]), session)
            session["messages"].append({
                "role": "tool", "tool_call_id": tc["id"],
                "content": json.dumps(result, ensure_ascii=False),
            })

        # ④ 裁剪必须在 user 边界切，否则会留下"孤立 tool 消息" → 接口 400
        trim_history(session)
    return "工具调用次数已达上限，请基于已有信息作答。"
```

**四个必须说出来的点**：
1. **轮数上限** —— 否则循环次数完全由模型决定（框架默认 `recursion_limit=10007`，实测能跑到 5004 次调用）
2. **消息配对** —— `assistant.tool_calls` 的 `id` 必须和 `tool` 消息的 `tool_call_id` 一一对应，缺一个就 400
3. **裁剪边界** —— 只能在 user 消息处切（`_trim_history`），否则孤立 tool 消息
4. **流式** —— 流式下 `tool_calls` 的 `arguments` 是**分片**到达的，要按 `index` 累加再 `json.loads`

**定位**：`tutor_agent.py:896`（`process_message`）、`:746`（`_stream_round`）、`:873`（`_trim_history`）

**自评**：能白板写出 + 说清 4 点 `[ ]` `[~]` `[x]`
