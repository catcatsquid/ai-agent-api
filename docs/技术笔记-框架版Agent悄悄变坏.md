# 技术笔记：一次"框架版 Agent 悄悄变坏"的排查

> 用途：面试讲稿 / 技术笔记素材。
> 场景：同一个课程答疑 Agent 有两条路径 —— LangGraph 的 Plan-and-Execute 图，
> 和我手写的 agent loop。我一直以为两条都能用，直到我把**同一句用户请求**分别打给它们。

---

## 一、结论先放前面

> **在 Agent 系统里，"工具结果要不要留在上下文里"这个看似不起眼的设计选择，
> 决定了多轮会话能不能成立。**

- **ReAct 图**把含 `ToolMessage` 的整段历史交给模型 → 上一轮工具结果里的
  `next_group_index` 留在**带内** → 模型看得见，跨轮状态自然存活。
- **Plan-and-Execute 图**为了让 planner 专注于规划，**主动把 ToolMessage 从历史里剔掉**、
  并把 assistant 内容截到 200 字 → 跨轮状态**无处安放**。

这个差异的后果不是"少个功能"，而是**整条刷题流程崩掉**：
模型编题、丢游标、绕过专用工具、把内部 JSON 漏进正文。

---

## 二、我是怎么发现的

起因是一个很朴素的对比实验：**同一句话，分别打给两条路径，看输出。**

请求序列：`我想刷计算机网络的选择题` → `继续下一组` → `第1题我不会，讲讲` → `另外出几道题`

| 场景 | Plan-and-Execute | ReAct |
|---|---|---|
| 出题 | ❌ 编造题目 + 编出 `https://example.com/net1.jpg` 这种**假图片链接** | ✅ 真实图片 `/qb_images/...` |
| 继续下一组 | ⚠️ **时好时坏**（见下） | ✅ 稳定给出第 2 组（题号 6–10） |
| 我不会 | ❌ 不调 `explain_question`，围绕知识点泛泛而谈 | ✅ 调了，并引用真实题干与答案 |
| 另外出题 | ❌ 工具**根本没注册** | ⚠️ 有工具 |
| 正文 | ❌ 漏出 `get_paper_questions {"paper_source": ...}` 原文 | ✅ 干净 |

**"时好时坏"这一段最值得记**：Plan 模式有时也推进了组号 ——
因为它可以从**自己上一轮发出去的文字**里读到"第 1/19 组"，从而推出该取第 2 组。
这比"稳定坏"更危险：**间歇性错误比稳定错误更难信任**，
用户会觉得"它有时候还挺聪明"，从而不会去排查。

---

## 三、根因不止一个（四个叠加）

1. **prompt 与代码不一致**
   `PLANNER_PROMPT` 把 `get_paper_questions` 写成"获取指定试卷的**所有**题目"，
   而工具实际一次只返回一组，且**完全没提 `group_index`**。
   → planner 的预期从一开始就是错的；它以为一次能拿到整卷，于是 synthesizer 拿不到题就开始编。

2. **工具集合三处不一致**
   注册 9 个工具、prompt 只列 8 个、`has_paper_tools` 白名单又漏一个 —— 漏的都是
   `explain_question`。→ **"学生说不会"这条路径在 Plan 模式下基本不可能被规划出来。**

3. **工具只返回"数据"，没有任何"该怎么呈现"的指引**
   手写助教的每个工具都带 `_guide`（"这一步只列清单，不要开始出题"），
   所以它不会编；Plan 路径的工具没有这层，模型认为"用户想刷题"还没被满足，**自己编题**。

4. **图是单向的：synthesizer 没有能力再取数据**
   `planner → executor → synthesizer` 走完就结束。一轮规划不够时，
   它只能编，或者**把工具调用当正文写出来**（实测漏过 JSON 原文）。

---

## 四、修法（分层，从便宜到贵）

### 第一层：改 prompt（几分钟，见效一半）
- 修正那句错的工具描述 + 补 `group_index` / `next_group_index`
- 工具数 8 → 9 → 10，把 `explain_question` 写进 prompt 与白名单
- 两个 prompt 都加**"不许编题"**硬规则（点名禁止占位图片地址、禁止把工具调用写进正文）

**结果**：`explain_question` 现在会被调用了，**但伪造题目还在**。

### 第二层：把"呈现契约"搬进工具返回值（半天，修掉伪造）
这就是关键的那一步 —— 和之前修"学生说不会"是**同一个原理**：

> 只给数据，模型就会自己组织，组织不出来就编。
> **给它成品文本和"这一步只做什么"的指引，它就没有编的空间。**

- `list_papers` 的返回里附上："本步只做一件事：把清单发给学生并问他选哪份，**不要开始出题**；
  绝不要自己编写题目、选项或图片链接"
- `get_paper_questions` 返回 ready-to-send 的 `reply_text` + `render_hint`

**结果**：伪造题目修掉了 ✅（实测第 1 轮如实列卷子，第 2 轮给真图片）。

### 第三层：给 Plan 图补上"跨轮会话游标"（route A）
- `AgentState` 加 `session` 字段：`{paper, type, group_index, next_group_index, qids, finished}`
- `executor_node` 从工具结果里**抽出游标**存进 state
  （只认自己生成的字段，解析不出来就原样不动游标）
- `planner_node` 把游标**显式组进 prompt**："刚出到第 1 组，下一组要传 group_index=2，qids=…"
- 顺带补上 `prepare_custom_quiz`（"另外出题"这条需求在 Plan 路径上此前**没有工具**）

**结果**：连跑 3 轮，**3/3 稳定推进**（修复前是时好时坏）✅

## 五、可复用的三条经验

1. **"工具结果留在上下文里"是一个架构决策，不是实现细节。**
   它直接决定跨轮状态能否在带内传递。选中"每轮丢弃工具结果以省 token"的范式时，
   必须**显式补一个状态容器**，否则多轮会话就是坏的。

2. **间歇性错误比稳定错误更危险。**
   当模型能从"自己上一轮说过的话"里反推出正确参数时，错误率会随对话措辞波动 ——
   测试一次通过不代表修好了。**验证这类问题必须连跑多次看稳定性**，
   而不是跑一次看结果对不对。

3. **"忘改 prompt"这类 bug 只能用一致性断言挡。**
   工具注册在 `tools.py`，描述写在 `nodes.py` 的 prompt 里，白名单又写在第三个地方 ——
   加一个工具要改三处，必然漏。所以我加了**枚举式断言**：
   "注册的工具必须都出现在 prompt 里"、"prompt 声明的工具数必须等于实际注册数"、
   "白名单必须覆盖所有刷题工具"、"不能把 `get_paper_questions` 说成取整卷"。
   13 项测试，挡住这一类问题。

---

## 六、面试可以怎么讲（30 秒版）

> 我发现同一个 Agent 的框架版路径在多轮刷题上是坏的：它会**编造题目和图片链接**。
> 排查下来根因不是模型，而是**"工具结果要不要留在上下文里"这个设计选择**——
> ReAct 天然把工具结果留在消息里，跨轮状态在带内传递；
> 而我的 Plan-and-Execute 图为了让 planner 专注，主动把工具结果从历史里剔掉、
> 把 assistant 内容截到 200 字，结果**跨轮状态无处安放**。
>
> 我分三层修：先改 prompt 里描述错误的工具说明（只修好一半），
> 再把"呈现契约"搬进工具返回值 —— 给它成品文本和"这一步只做什么"，
> 它就没有编题的空间；最后给状态加会话游标、由 executor 抽取、planner 显式读取，
> 连跑 3 轮才稳定。
>
> 这里我最想说的一个教训是：**这个 bug 是时好时坏的** ——
> 模型偶尔能从自己上一轮发出去的文字里推出正确参数，所以跑一次会通过。
> 验证这类问题必须看多次运行的稳定性。
