# 案例：手写助教（LLM 助教）的完整生命周期

> **本文由两篇旧文档合并而成**：`llm_tutor_refactor.md`（为什么做、对照为什么没做成）
> + `技术笔记-两条Agent路径的追平与定位.md`（怎么对比、怎么追平、为什么撤）。
> 合并的原因：这个组件的"为什么创建 → 用来干嘛 → 对照失败 → 补做对照 → 为什么撤掉"
> 原本被切成两半，任何一篇都讲不完整。
>
> **现在的状态一句话**：代码与接口保留（`course_agent/tutor_agent.py`、`POST /tutor/stream`），
> 但**不从界面进入**，定位是**冻结的对照实现** —— 新能力只加到 BOT，它不再跟着演进。
>
> 时间线：`09-30` 创建（取代状态机）→ `10-03` 第一次进 git → `10-04` 与 BOT 同题对比并追平
> → `10-04` 界面撤掉入口。

---

## 一、为什么创建它

两个层面的动机，别混为一谈。

### 1.1 产品动机（主要、成立）

我作为使用者，希望这个 Agent **天生就懂我的学习/复习习惯** —— 逐节教、小节测、错了重刷、
复习优先刷错题 —— 而不用每次开对话都把这些流程再说一遍。这是项目的差异点，
也命中我自己的真实使用需求。

### 1.2 技术动机（次要、**未达成**）

顺便拿它跟**原来的 Python 状态机版**比一比，验证「LLM 主导会不会更灵活」。

被它取代的状态机是 `09-30` 提交的 `learn.py` + `review.py`（共约 900 行）。
状态机的问题很具体：

```
新会话: 解析课程章节 → KB检索 → LLM生成大纲 → 教第1节 + 出小测题
quiz_pending: 用户提交答案 → 批改讲解
...
```

它靠 `_is_quiz_answer(text)` 这类**硬编码意图判断**分流 ——
一旦用户的说法不在预期内就分流错。例如刷题时说「换一套卷子」会被**当成答案批改**。

### 1.3 重构方向：让 LLM 主导对话

通过 Function Calling 调用工具（知识库检索、习题库、批改等），
把「该做什么」交给模型判断，而不是用 Python 写死状态流转。

| 方案 | 内容 | 结果 |
|---|---|---|
| **方案 A：手写工具调用循环** | 自己写 `_stream_round` 调 API、解析 SSE 增量与 `tool_calls` 分片；主循环 `process_message`：LLM → 看 tool_calls → 执行工具 → 结果回传 → 再调 LLM → 无工具则输出；最多 6 轮；会话在 `_SESSIONS`（带 TTL） | **已实现** = 现在的 `tutor_agent.py` |
| **方案 B：LangGraph 版助教** | 计划用 `StateGraph` + `ToolNode` 复用 `graph.py` 风格，**以便和方案 A 做真正的对照** | **从未实现**（`lg_tutor.py` 不存在） |

## 二、它当时用来干嘛（以及按真实吐槽迭代的 5 轮）

### 2.1 能力清单

| 工具 | 作用 |
|---|---|
| `list_papers` | 按课程列试卷（默认两门课都列） |
| `get_paper_questions` | 分组出题：选择/填空/判断 5 题一组，综合题 1 题一组 |
| `explain_question` | 取题面 + 参考答案 + 参考要点，用于讲题 |
| `prepare_custom_quiz` | 取「临时出题」的素材（题目由模型自己写） |
| `grade_answers` | 批改（选择/判断精确判定，填空/综合按参考要点评分） |
| `search_knowledge_base` | 知识库检索，可按课程过滤 |
| `get_practice_stats` / `record_practice` | 练习次数统计 |
| `list_course_sections` / `read_section` / `record_study_position` | 学习/复习三件套（后来与 BOT 对齐时补的） |

### 2.2 它是被真实使用推着长出来的

上线后我自己天天用，然后按真实吐槽迭代了 5 轮。三个最有代表性的：

1. 说「我不会」时它**讲不了题** —— 因为防泄题把题面也从模型手里拿走了
   → 加了按需取题的 `explain_question`
2. 答 `AAAAA` 它认不出来，当成「你没提交答案」
   → 放宽解析，并把「格式判断」交给工具（契约写进返回值）
3. 说「继续刷题」却**不出题**（只嘴上答应）
   → 把清单做成成品文本 `reply_text`，并在循环里加了一次**确定性纠偏**

## 三、那个对照实验为什么没做成

**方案 B 缺失，所以对照从头到尾没有发生。** 实际发生的是**单方面替换**：

- `learn.py` / `review.py` 已删除（连带的 `chapter_utils.py` 失去全部调用方，一并删除）
- 删除是**单向的**：状态机那 782 行里已经调通的流程（逐节教学、小测批改、
  章节总复习、错题重刷）在助教里**并没有一一对应地重建**

也就是说，「只用来对比」这个说法与实际结果不符：**对比的一半缺失，被比较的对象却已经被移除。**

> 另一个诚实细节：`tutor_agent.py` 在 `10-03` 之前**从未进过 git**（一直是未跟踪文件）。

## 四、「LLM 主导更灵活」这个假设的实测结论

当初的直觉是「LLM 主导会更灵活」。有数据之后的结论是：
**部分成立，但代价被低估了。**

### 4.1 灵活性没有换来正确性

两个运行面现在共用 `course_agent/qbank.py` 与 `quiz_service.py`，所以
**分组出题、不泄题、按题型精确批改的行为完全一致**。差异只在**编排层**，不在**能力层**。

### 4.2 自由度需要靠「把结构补回去」来兜底

助教这一路修下来，几乎每一条新增约束都是在把框架/状态机本来能**结构性保证**的东西重新装回去：

| 后来补上的约束 | 它解决什么 | 状态机里对应的东西 |
|---|---|---|
| `reply_text` 成品文本 | 模型转录 8 份卷子时漏了 3 份 | 列表本来就是代码拼的字符串 |
| 课程守卫 | 模型在「我想刷题」时自己填 `course`，藏了一半题库 | 课程是路由参数 |
| `prepare_custom_quiz` + 范围守卫 | 模型拿计网题冒充死锁题 | —— |
| 答案格式契约 | 模型把 `AAAAA` 当成「你没提交答案」 | `_is_quiz_answer`（但过于死板） |
| `explain_question` | 模型手里没题目，讲不了题 | 状态机直接持有题面 |

有意思的是最后两行：`_is_quiz_answer` 正是当初被嫌弃的「写得太死」，
而助教最后也长出了 `_wants_custom_quiz()` + 答案格式契约 —— **同一个问题的弱化版**。
两者不是「死板 vs 灵活」，而是**同一条光谱上的两个点**。

### 4.3 手写循环里约 330 行（≈28%）在重造框架白给的东西

```
_stream_round     61 行   SSE 解析 + tool_call 分片拼装
process_message  116 行   主循环
_chat_json        31 行   非流式调用 + JSON 解析 + 429 重试
_post_stream      24 行   带退避的流式请求
_new_session/get_session/sweep_sessions  27 行   会话与 TTL
_compact_tools/_trim_history             30 行   上下文治理
_tool_label/_tool_summary                40 行   前端事件
------------------------------------------------
合计约 329 行 / 全文件 1197 行（后来长到 1284 行）
```

LangGraph 的 `StateGraph` + checkpointer + `ToolNode` 直接提供这些。

## 五、补做对照：BOT vs 助教同题对比

后来我在认真考虑「还要不要留着它」，于是**把它跟路线内的 BOT 做了一次真正的对照** ——

> ⭐ 这**正是当初那个没做成的对照**，只不过对手从「状态机」换成了「路线内的 LangGraph Agent」。

### 5.1 先厘清：两条路径各自「遵照什么」建起来

**BOT（LangGraph）—— 按十周路线**，逐周都能在代码里找到证据
（核查脚本 `debug/verify_roadmap_coverage.py`）：

| 周 | 路线要求 | 代码证据 |
|---|---|---|
| 1 | FastAPI + SSE 流式 | `server.py`、`sse_content_event` |
| 2 | RAG + 向量搜索 | `rag_tool.py` + ChromaDB |
| 3 | ReAct 多工具 Agent | `archive/week1-week3/week3-react-agent`（手写版，已归档） |
| 4 | LangGraph ReAct + 流水线 + 守卫节点 + B3 测试 | `graph.py`/`nodes.py`、`knowledge_pipeline/`、`web_search_fallback` |
| 5 | Web 搜索 + Plan-and-Execute + 多轮持久化 | `web_search`、`planner_node`、`MemorySaver` |
| 6 | 双模式流 + 端到端测试 + 盲区修复 | `react_graph`、`RELEVANCE_THRESHOLD` 修复 |
| 7 | 全局异常 + 日志 + trace_id + 配置 | `errors.py`、`logger.py`、`config.py` |
| 8 | 混合检索 + Rerank + Docker + 压测 + 管理界面 + 题库 | `_hybrid_search`、`_llm_rewrite_query`、`Dockerfile`、`locustfile.py`、`kb.html`、`qbank.py` |
| 9 | 开源阅读 + 手写 Agent | 手写 Agent ✅（本文这个）；**开源阅读 ❌ 没做** |
| 10 | 面试冲刺 | `docs/面试自测清单.md` |

**超出路线的部分**（repo 里有、路线表没列）：鉴权与默认拒绝守卫、限流/请求日志中间件、
CI、前端行为断言、`quiz_service`（架构去重）、`doc_utils`（断循环依赖）。
—— 这些是后来按真实问题补的，**不属于路线**。

### 5.2 对比方法与一个重要的坑

同一段学生脚本、同样 5 个场景，两个运行面各跑一遍。判据全部是
**学生视角能感知到的**（不是「有没有调工具」这种实现视角）：

```
我要复习操作系统 → 我答一下：1.B 2.D 3.对 4.银行家算法 → 第二题我没懂，换个讲法
→ 现在换计算机网络，我要复习传输层 → 那刷几道传输层的题吧
```

信号分「好/坏」两类，坏的权重更高。跑多轮取一致性。

**⚠️ 我的探针错了两次（这一节比结论更值得记）**：

第一轮我得出过「助教把学习流程弄坏了」的结论，**那是错的**：

1. **发错了字段名**：助教接口要 `session_id`，我发的是 `thread_id` → 被忽略
   → **每一轮都是新会话、状态全丢**。我看到的「没有记忆」是探针造出来的。
2. **抓错了事件名**：助教发 `{"type":"tool"}`，我只抓 `{"type":"node"}`
   → 误判「工具根本没被调用」。

改对之后，真实表现**本来就比我说得好**：学生交小测答案时助教**不调工具、自己逐题批**。

判据本身也修过一次：一开始用「回复里有没有文件名」判断「读对了章」，
被「工具提示里带了文件名」误导；改成「有没有该章的内容关键词」才准。

### 5.3 第一轮：BOT 明显吃亏

```
合计        BOT 好17 / 坏16   |   助教 好27 / 坏5
  开始复习      BOT 6/3   助教 9/0
  说没听懂      BOT 2/4   助教 6/0
  按知识点刷题   BOT 0/5   助教 3/0
  交小测答案    BOT 3/3   助教 3/2
  换一门课      BOT 6/1   助教 6/3
```

典型失败：
- 「我要复习操作系统」→ 讲了，但**不说「本节结束」、不出小测**
- 「我答一下…」→ **「请提供具体的问题和选项」**（手里没有小测题，批不了）
- 「第二题没懂」→ **自己编了一道题**（「假设我们讨论的是…以下是一个可能的问题」）
- 「刷几道传输层的题」→ **只给试卷菜单**（「请告诉我选哪一份」）

### 5.4 三处根因（**关键的那一处不是范式问题**）

**根因 1：⭐ 状态注入放错了位置**

```python
# BOT
planner_node     里出现 study: True     ← 学习书签只喂给了「规划器」
synthesizer_node 里出现 study: False    ← 「写回答的模型」看不到

# 助教
_system_prompt_for(session) → messages[0]   ← 写回答的模型直接看得到
```

「本节结束 / 出小测 / 小测由你自己批」这些是写给**写回答的模型**的契约，
BOT 却只把它交给了规划器。尤其「学生交小测答案」那一轮**一个工具都不会调**
（走 `CHITCHAT_PROMPT`），所以那段契约在 BOT 侧根本到不了模型手里。

**根因 2：两条守卫只在助教有**

- **「没看到题目」→ 确定性重发**（学生报过这个 bug）
- **历史裁剪 + 工具结果压缩**（BOT 的 `MemorySaver` 原来**没有任何上限**，审查文档 F2）

**根因 3：planner 缺「看宾语」的路由规则**

- 「刷几道**传输层**的题」= 按知识点练 → 该用 `prepare_custom_quiz`；
  而 planner 的规则 1（「刷题 → list_papers」）先命中，于是永远给菜单。
  题库没有按知识点组卷，**给菜单等于没满足需求**。
- 「没听懂/换个讲法」→ 该 `read_section` 重取原文；planner 没想到。

### 5.5 五处修复

| # | 修什么 | 怎么修 | 效果 |
|---|---|---|---|
| 1 | synthesizer 看不到会话状态 | 新增 `_session_block()`，同时拼进 `SYNTHESIZER_PROMPT` 与 `CHITCHAT_PROMPT` | **没有直接拉升分数** —— 它是前置条件 |
| 2 | 没有重发守卫 | planner 里加**确定性覆盖**：学生说「没看到题目」且有当前组 → 强制重发那一组 | 「没看到题目」不再只得到道歉 |
| 3 | 历史无上限 | 按 **user 消息边界**裁剪 + 较早的工具结果正文换占位符；保证 assistant(tool_calls) 与 tool 成对（不留孤儿） | F2 缓解 |
| 4 | 按知识点刷题走错 | planner 规则补「看宾语」：按知识点的练习 → `prepare_custom_quiz` | 0/5 → 2/0 |
| 5 | 讲课中交答案去调题库 | 新增 `_looks_like_quiz_answer()`；讲课中且无当前试卷时**这一轮不规划任何工具** | 3/3 → 2/0 |

> ⚠️ **一个值得注意的细节**：最有洞察力的那处修复（#1 状态注入位置）**没有直接拉升分数**。
> 它只是让契约「能到达」写回答的模型；真正让分数动的是 #4 和 #5 这类**路由与守卫**。
> 也就是说：**「找到根因」和「指标改善」不是同一件事，别用指标反过来否定根因判断。**
> （#1 的价值在后面才显出来：没有它，#5 那条守卫即使拦住了题库调用，
> 模型手里也没有「小测由你自己批」的契约。）

**修复过程中的数据变化**（每轮 = 5 个学生场景）：

```
第一轮（已含 #1，但缺路由规则与守卫）   BOT 好17 / 坏16    助教 好27 / 坏5
第二轮（再补 #4 路由规则）             BOT 好15 / 坏8     助教 好18 / 坏2   ← 「说没听懂」已拉平 4/0
第三轮（再补 #2 #3 #5 三条守卫）        BOT 好16 / 坏3     助教 好18 / 坏2   ← 基本持平
```

第三轮逐项：交小测答案 2/0＝2/0 ✅、说没听懂 4/0＝4/0 ✅、按知识点刷题 2/0＝2/0 ✅、
换一门课 4/1≈4/2、**开始复习 4/2 < 6/0**（BOT 说「本节结束」仍不稳定）。
耗时：BOT 289.7s vs 助教 250.2s。

## 六、⭐ 代价结构（这才是决策的关键输入）

**BOT 不是「做不到」，而是每加一种行为契约，都要想清楚两件事**：
它该注入**哪个节点**（planner 还是 synthesizer？），以及该写**哪条路由规则**。
而手写循环把这些压在同一条链路上，状态直接进回答阶段，「自然地就有」。

> **BOT 的灵活性来自分工，成本也来自分工。**

这条在本项目里被验证了**三次**：

1. 刷题工具：两个运行面各写一份 → 真实分叉（一边缺 `basis_warning`、题号口径也不同）→ 合并到 `quiz_service`
2. 学习/复习工具：只做了 BOT 侧、**漏了助教侧** → 加 `tests/test_surface_parity.py` 强制对齐
3. 行为契约：`_guide` 谁看得见？ → 就是这次踩的坑

所以「两条都留」的**真实成本**是：新能力要么实现两遍，要么用共享层 + 一致性测试把它钉住。

## 七、为什么最后把它从界面撤掉

**决定**：日常只有 BOT 一条产品路径；手写助教**冻结为对照实现**。

**理由（两条，都是可验证的）**：

1. **能力已等价** —— 同题对比 5 个场景：BOT 16好/3坏，助教 18好/2坏。
   留两个入口只增加「该用哪个」的困惑，而**能力上没有增量**。
2. **维护成本是真实的** —— 见上一节，同一个错误在本项目里发生过**两次**
   （刷题工具分叉、学习工具漏同步）。

**具体怎么做（可逆）**：

- 撤掉侧栏的「模式」切换（`知识寻回BOT` / `LLM助教` 两个按钮），`currentAppMode` 恒为 `qa`
- 原按钮位置留注释，写明**原因与恢复方式**（把两行按钮贴回去即可）
- JS 里的 tutor 分支标注「平时走不到，保留是为了对照」
- **代码与接口全部保留**：`tutor_agent.py`、`POST /tutor/stream`、
  `tests/test_tutor_agent.py`、`tests/test_surface_parity.py` 照跑

**验证方式**：去掉 HTML 注释后检查活动标记 ——
「LLM助教」字样 0 次、模式按钮 0 个、`setAppMode` 调用点 0 处；
`POST /tutor/stream` 仍返回 200 且有正文流。

## 八、两条路径的机制差异清单

这张表是本文最"可迁移"的部分 —— 每一行都能展开成一次技术选择。

| 维度 | BOT（LangGraph） | 助教（手写循环） | 取舍 |
|---|---|---|---|
| 状态注入 | 分节点（planner 看得到、synthesizer 原本看不到） | 直接进 system prompt | 分工带来灵活性，也带来「注错了没人发现」的风险 |
| 跨轮状态 | `AgentState["session"]`，由 executor **从工具结果里抽** | handler 里**直接写** session | 抽取式解耦但要解析约定；直写简单但耦合 |
| 工具路由 | planner 出 JSON 计划 + 代码守卫 | 模型每轮自己选 + 代码守卫 | 计划式可一次规划多步；单循环更贴上下文 |
| 上下文治理 | LLM 摘要压缩（摊还缓存） | 窗口 + 工具结果压缩 + 历史裁剪 | 摘要省 token 但多一次 LLM 调用；压缩直接但粗暴 |
| 流式 | 框架 `astream` + 统一事件函数 | 自己拼 `tool_calls` 分片 | 手写那套**能看清协议细节**，框架那套代码少 |
| 会话生命周期 | MemorySaver（原来无上限） | TTL 3 小时回收 | 各有取舍，现在 BOT 也加了裁剪 |
| 失败纠偏 | 代码守卫（重发/小测答案） | 代码守卫 + **一次 nudge** | 守卫式比提示词可靠（实测三次升级才治住） |
| 重启后 | 学习/刷题进度**能恢复**（落盘） | **全丢** | BOT 更适合长会话 |
| 联网搜索 | 有 | 没有 | BOT 工具面更宽 |
| 代码量 | 图+节点+state 969 行（+memory 306） | 1284 行 | 手写那条约 28% 在重造框架能力 |

## 九、可复用的教训

1. **测 Agent 之前先验证测量工具** —— 字段名、事件名、判据，任一个错都会让你得出错误结论
   （本文第 5.2 节两次误判都源于此）。
2. **判据要放在「用户能感知的结果」上**，不要放在实现细节（工具名/节点名）上。
3. **想在框架里加行为契约，先问「这个契约该给哪个节点」** ——
   给错了节点，再好的契约也不生效（本次最贵的一课）。
4. **「提示词写不要用」通常不够** —— 要治好「讲课中跑去做题库批改」用了三级升级：
   提示词（不跟）→ 工具入口守卫（还不跟）→ **干脆不提供这些工具**。
5. **「对照实验」要在删除被比较对象之前做完** —— 本文第 3 节就是这个教训的实例：
   状态机被删了，对照才想起来没做。
6. **多出来的自由度，最后都要用结构补回去** —— 见第 4.2 节的表；
   这不是「灵活 vs 死板」，而是同一条光谱的两个点。
